# Research: exact checkout and Splash 1.1.0

Research date: 2026-09-28. Target Git checkout is /Users/do/git/opencode on local branch dev, with Spec Kit feature 002-splash-telemetry. The spec and constitution were already staged when planning began. Evidence below is from this checkout, its installed packages, the locally installed Splash executable and packaged source, and Splash tag 1.1.0.

**Decision**: Reuse beginAttemptTelemetry, the fallback source, EffectBridge, session.telemetry, app store, and session-ui/timeline presentation. Extract only provider-neutral ownership/acceptance types currently named under MLX.

**Rationale**: [llm.ts](../../packages/opencode/src/session/llm.ts) lines 428–523 creates the attempt before provider setup, resets the previous terminal at 447–461, starts fallback at 462–489, discards setup failure at 493–501, finalizes or discards by stream exit at 503–509, and converts the AI SDK fullStream at 515–522. The provider acceptance check at 261–279 marks providerDecodeAccepted before forking publication; the fallback repeats suppression inside the scheduled Effect at 466–486. [attempt-telemetry.ts](../../packages/opencode/src/session/llm/attempt-telemetry.ts) lines 3–62 already owns provider/fallback attachment, idempotent finalize/discard, and late attach discard. [fallback-telemetry.ts](../../packages/opencode/src/session/llm/fallback-telemetry.ts) lines 64–104 and 132–201 supplies bounded live samples, measured-sample eligibility, step/tool interval handling, finalization, and discard; live throttle is 250 ms and a rate needs a positive token count and at least 50 ms. [mlx-telemetry.ts](../../packages/opencode/src/session/llm/mlx-telemetry.ts) lines 1–61 defines the current provider-neutral holder/rate predicate under an MLX name; its /events watcher and attribution begin at 63 onward and remain a regression contract.

The normalized event already carries phase, counts, rate, done, source, and approximate ([SessionV1.Event.Telemetry](../../packages/schema/src/v1/session.ts), lines 659–672). [app projection](../../packages/app/src/context/global-sync/telemetry.ts) lines 3–30 and [reducer](../../packages/app/src/context/global-sync/event-reducer.ts) lines 274–285 store it by session and AssistantMessage; [server-session](../../packages/app/src/context/server-session.ts) lines 1033–1041 has the parallel app entry. [session-ui helpers](../../packages/session-ui/src/components/generation-telemetry.ts) lines 1–109 validate positive finite displayed rates, format progress and approximate marker, and select terminal rates. [timeline](../../packages/app/src/pages/session/timeline/message-timeline.tsx) lines 164–170, 1015–1029, and 1241–1263 renders thinking and completed rates. No UI/store/schema change is justified.

Existing tests: [fallback tests](../../packages/opencode/test/session/fallback-telemetry.test.ts) cover estimator semantics; [MLX tests](../../packages/opencode/test/session/mlx-telemetry.test.ts) cover watcher lifecycle, attribution, short generation, and arbitration; [LLM tests](../../packages/opencode/test/session/llm.test.ts) lines 2406–2661 cover retry/setup/fallback; [provider tests](../../packages/opencode/test/provider/provider.test.ts) lines 2139–2197 cover sanitization. ## Decision 2 — Use the installed SDK request/stream seams

**Decision**: Do not set or inject return_progress; passively observe whatever the normal request already produces, and inspect raw parts on the same fullStream before LLMAISDK.toLLMEvents. Enable raw chunks only for the opted-in Splash branch on the already-selected AI SDK path. Do not add a custom fetch wrapper, a second inference request, a polling loop, or a new shared LLMEvent.

**Rationale**: Exact versions from [packages/opencode/package.json](../../packages/opencode/package.json) lines 71, 73, 113, [root package.json](../../package.json) line 67 and [bun.lock](../../bun.lock) entries are ai 6.0.168, @ai-sdk/provider 3.0.16, @ai-sdk/openai-compatible 2.0.41. Installed ai 6.0.168 dist/index.d.ts lines 2889–2895 exposes includeRawChunks; dist/index.js lines 7283–7293 passes it to each doStream, 7483–7487 forwards raw, and 7766–7775 includes raw in fullStream. Installed @ai-sdk/provider 3.0.16 dist/index.d.ts lines 1953–1955 defines the raw provider part as an object with type raw and rawValue unknown. OpenCode currently enables raw only for Copilot ([llm.ts](../../packages/opencode/src/session/llm.ts) lines 365–366), then [LLMAISDK.toLLMEvents](../../packages/opencode/src/session/llm/ai-sdk.ts) lines 277–281 only extracts Copilot billing and returns no LLMEvents for raw parts.

Installed openai-compatible 2.0.41 dist/index.js lines 434–439 sets providerOptionsName to configured name split at dot and trimmed; lines 465–493 handle both provider-specific and known option names; lines 541–550 copy unknown selected options directly to top-level body. This is the general pass-through this feature does not need: Splash telemetry adds no keyed option. OpenCode passes model.providerID as provider name ([provider.ts](../../packages/opencode/src/provider/provider.ts) lines 1873–1881) and [ProviderTransform.providerOptions](../../packages/opencode/src/provider/transform.ts) lines 1462–1478 computes the same split key. OpenCode already sets includeUsage true for openai-compatible unless disabled ([provider.ts](../../packages/opencode/src/provider/provider.ts) lines 1845–1847); SDK dist/index.js lines 644–652 sends stream_options.include_usage. The installed SDK has transformRequestBody and metadataExtractor in provider settings (openai-compatible dist/index.d.ts lines 271–281; dist/index.js lines 1720–1725). metadataExtractor.processChunk receives parsed chunks but builds metadata only at finish (dist/index.d.ts lines 53–68; dist/index.js lines 694, 892–906); placing live side effects in cached provider construction would make attempt attribution and failure isolation harder than raw fullStream observation. transformRequestBody and any keyed option mutation are unnecessary because this feature adds no request field: return_progress, if present, arrives through ordinary provider/request configuration and travels to the wire unchanged.

**Parser compatibility gate**: The installed openai-compatible stream parser uses a loose object but requires choices to be an array (dist/index.js lines 961–997). Splash 1.1.0 progress frames do include a normal choices entry. Raw parts are enqueued before normalized parse handling (dist/index.js lines 684–694). The implementation fake server must prove this exact frame traverses fullStream without a stream error.

**Alternatives considered**: injecting return_progress because splashTelemetry is enabled (changes the inference request), forcing the AI SDK runtime for a model that dispatch would send elsewhere (changes generation transport), custom fetch/request wrapper (duplicates transport), metadataExtractor callbacks (provider-cache and stream-path coupling), post-adapter raw event (requires unnecessary shared LLMEvent), polling (wrong source and attribution).

The experimental native runtime is a separate dispatch branch. [native-runtime.ts](../../packages/opencode/src/session/llm/native-runtime.ts) lines 54–59 can accept provider IDs openai, anthropic, or opencode-prefixed with an OpenAI-compatible package, but lines 90–145 returns only normalized LLMEvents and has no Splash raw-chunk seam. [llm.ts](../../packages/opencode/src/session/llm.ts) lines 294–349 selects native before AI SDK when the feature flag is on. Telemetry must not change that selection: an enabled Splash model that dispatch sends to native stays on native, and native Splash telemetry is simply unavailable while existing fallback behavior remains. This feature observes raw metadata only when the already-selected path exposes it. For the normal `splash` provider using @ai-sdk/openai-compatible, the AI SDK raw-stream observer applies because that is already its normal generation path, not because telemetry redirected it. A standard custom Splash provider ID is already unsupported by native and naturally falls through to AI SDK.

## Decision 3 — Keep the two sanitization boundaries

**Decision**: Use splashTelemetry: true as an explicit OpenCode provider option and strip it at the same two boundaries used by mlxTelemetry. The control reaches neither SDK constructor options nor any inference request body; this feature adds no Splash protocol field of its own.

**Rationale**: There is no generic native-telemetry configuration seam in this checkout. [provider.ts](../../packages/opencode/src/provider/provider.ts) lines 1832–1869 copies provider options, removes mlxTelemetry before cache-key construction and SDK factory setup, and resolves the effective URL. [llm.ts](../../packages/opencode/src/session/llm.ts) lines 236–239 removes mlxTelemetry from the per-request option copy before native runtime or ProviderTransform.providerOptions. The latter mapping at lines 387 and [transform.ts](../../packages/opencode/src/provider/transform.ts) lines 1421–1478 otherwise passes model options onward. [Provider.getEndpoint](../../packages/opencode/src/provider/provider.ts) lines 1786–1830 and 1914–1922 shares dispatch URL precedence and interpolation; no new endpoint logic is needed for stream-native Splash. mlxTelemetry stays supported exactly as before. Enabling splashTelemetry must leave the captured SDK constructor options and the HTTP body byte-identical to the opt-off case, for Splash and for every other provider. Raw observation applies only to an explicitly opted-in Splash model on the OpenAI-compatible SDK route; return_progress is never added by OpenCode for any provider.

**Alternatives considered**: Generic telemetry plugin framework (two real adapters need only small shared ownership), auto-injecting return_progress when splashTelemetry is enabled (changes the inference request), silently applying Splash request fields to all compatible providers (behavior change), putting the OpenCode control itself into providerOptions (leak).

## Decision 4 — Match the installed Splash 1.1.0 protocol

**Decision**: Passively map request-local prompt_progress to normalized prefill when such chunks are present; keep fallback for live decode; accept a finite positive predicted_per_second as provider-native only when exactly one terminal timing was observed in the attempt. Treat zero terminal timings as unavailable, exactly one observed timing whose predicted_per_second is not finite and positive as unavailable, and more than one terminal timing observed in one attempt as ambiguous regardless of rate validity, failing closed to fallback. Do not poll /status or /metrics and do not add return_progress.

**Rationale and provenance**: /opt/homebrew/bin/splash --version reports Splash 1.1.0; Homebrew incoai/tap metadata reports 1.1.0. The installed packaged server.py, metrics.py, runtime.py, and api_shapes.py match the [Splash 1.1.0 tag](https://github.com/incoai/splash/tree/1.1.0) byte for byte (tag commit 3e1f9ece3e2528f3eb46b82a05911591f34a4317). [Version-pinned development documentation](https://github.com/incoai/splash/blob/1.1.0/DEVELOPMENT.md#L641-L680) and [request validation](https://github.com/incoai/splash/blob/1.1.0/server/server.py#L572-L582) specify top-level return_progress true only for stream true. [Chat stream implementation](https://github.com/incoai/splash/blob/1.1.0/server/server.py#L1518-L1539) and [shape](https://github.com/incoai/splash/blob/1.1.0/server/api_shapes.py#L1033-L1057) put prompt_progress at the top level of a normal chat.completion.chunk with choices:[{index:0,delta:{},finish_reason:null}]. It has total, cache, processed, and time_ms. The [native progress producer](https://github.com/incoai/splash/blob/1.1.0/server/runtime.py#L291-L310) rejects repeats/regressions. total is prompt tokens; cache is initial cached tokens; processed is current prefill progress; time_ms is elapsed prefill observation, not an ETA. [Protocol tests](https://github.com/incoai/splash/blob/1.1.0/dev/tests/engine/test_prompt_progress.py#L38-L120) show progress with total 2, cache 0 or 1, processed 0/1 then 2, time_ms 0.0 then 1.0.

[Chat finish and usage implementation](https://github.com/incoai/splash/blob/1.1.0/server/server.py#L1561-L1591) puts timings on the finish-reason chunk, then emits a separate choices:[] usage chunk when stream_options.include_usage is true. timings has prompt_n, cache_n, predicted_n, prompt_ms, predicted_ms, prompt_per_second, predicted_per_second. [Timing calculation](https://github.com/incoai/splash/blob/1.1.0/server/metrics.py#L220-L276): prompt_n is full prompt count, cache_n cached prompt count, and prompt_per_second uses uncached prompt tokens over prompt_ms; predicted_n is full completion count, predicted_ms measures first emission to completion; predicted_per_second excludes the complete first emission (possibly a speculative token batch) and divides subsequent measured decode tokens by first-emission-to-completion duration. prompt_ms is native start to first emission, excluding admission queue; these durations are not client wall time and need no local reconstruction. Zero predicted_per_second signals unavailable, including a one-emission response, not 0 tok/s. [Timing tests](https://github.com/incoai/splash/blob/1.1.0/dev/tests/engine/test_response_timings.py#L63-L103) exercise these cases.

The same optional usage chunk carries request-local metrics.decode.tokens and metrics.request_latency.first_token_to_done_ms ([server](https://github.com/incoai/splash/blob/1.1.0/server/server.py#L1570-L1591), [metrics serializer](https://github.com/incoai/splash/blob/1.1.0/server/metrics.py#L284-L291)). This feature does not parse them: no multi-step aggregation is built, and terminal rate arbitration uses only timings.predicted_per_second. /status.metrics.decode_tokens_per_second is an aggregate ([version-pinned documentation](https://github.com/incoai/splash/blob/1.1.0/DEVELOPMENT.md#L649-L666), [metrics](https://github.com/incoai/splash/blob/1.1.0/server/metrics.py#L170-L183)); /metrics is aggregate as well. The installed 1.1.0 streaming implementation offers no request-local live decode signal. Therefore no status polling is admissible for an AssistantMessage rate.

**Illustrative protocol-faithful payloads** (IDs, created value, and model are illustrative; structure and field names are from the pinned source):

~~~json
{"model":"test-model","messages":[{"role":"user","content":"Hi"}],"stream":true,"stream_options":{"include_usage":true}}
{"model":"test-model","messages":[{"role":"user","content":"Hi"}],"stream":true,"return_progress":true,"stream_options":{"include_usage":true}}
{"id":"chatcmpl-123","object":"chat.completion.chunk","created":123,"model":"test-model","choices":[{"index":0,"delta":{},"finish_reason":null}],"prompt_progress":{"total":2,"cache":1,"processed":1,"time_ms":0.0}}
{"id":"chatcmpl-123","object":"chat.completion.chunk","created":123,"model":"test-model","choices":[{"index":0,"delta":{},"finish_reason":"stop"}],"timings":{"prompt_n":2,"cache_n":1,"prompt_ms":1.0,"prompt_per_second":1000.0,"predicted_n":5,"predicted_ms":2.0,"predicted_per_second":1500.0}}
{"id":"chatcmpl-123","object":"chat.completion.chunk","created":123,"model":"test-model","choices":[],"usage":{"prompt_tokens":2,"completion_tokens":5,"total_tokens":7},"metrics":{"decode":{"tokens":3},"request_latency":{"first_token_to_done_ms":2.0}}}
~~~

The first request line is the baseline: splashTelemetry adds no field. The second is the independent case where ordinary provider/request configuration already sets return_progress, which is what makes Splash emit prompt_progress. Each response line above is the JSON after an SSE data: prefix; the stream ends with data: [DONE]. The first-emission batch has two tokens in this illustrative timing example, so (5−2) / 0.002 = 1500 tok/s. The real usage chunk may carry additional metrics keys, which this feature ignores.

**Alternatives considered**: Treating zero as a measured rate; deriving predicted_n/predicted_ms; using aggregate status throughput for a request; inventing a live native decode signal. All misstate the source.

## Decision 5 — Step, retry, and terminal semantics

**Decision**: Scope raw collection to an attempt and AI SDK step. In the current call path there is at most one successful provider stream per llm.stream invocation. Hold final timing until successful stream finalization. Count every recognized terminal timing observation before rate validation, and detect more than one observed terminal timing within one attempt and fail closed to the existing fallback regardless of whether any of those timings contain a valid rate; never aggregate, average, or substitute the last step.

**Rationale**: [llm.ts](../../packages/opencode/src/session/llm.ts) lines 350–424 calls streamText without stopWhen; installed ai 6.0.168 defaults stopWhen to stepCountIs(1) (dist/index.js line 6459). The SDK requests another provider step only with executed tool output and unmet stop condition (dist/index.js lines 7602–7625). AI SDK maxRetries is passed at [llm.ts](../../packages/opencode/src/session/llm.ts) line 394 and applies before doStream returns (ai dist/index.js lines 7235–7240, 7283–7295), so retry attempts that never yielded a stream do not contribute raw final timings. [processor.ts](../../packages/opencode/src/session/processor.ts) lines 852–890 retries llm.stream under the same AssistantMessage ID, creating a new telemetry attempt; the outer prompt loop can create a new AssistantMessage for a later tool turn ([prompt.ts](../../packages/opencode/src/session/prompt.ts) lines 1222, 1262–1277). LLMAISDK already has start-step, finish-step, overall finish, and tool events ([ai-sdk.ts](../../packages/opencode/src/session/llm/ai-sdk.ts) lines 85–126 and 193–264). The fallback sums active per-step decode intervals and handles cumulative finish usage ([fallback-telemetry.ts](../../packages/opencode/src/session/llm/fallback-telemetry.ts) lines 113–130, 168–182).

If more than one successful provider step ever appears within one OpenCode attempt, prefill counts are step-local and reset on start-step; they cannot be summed across changing prompts. For terminal decode, the collector counts terminal timing observations, not valid rates: it increments for every recognized Splash terminal timing before any validation of predicted_per_second. With zero terminal timings observed, the native terminal rate is unavailable and fallback remains eligible. With exactly one terminal timing observed, its timings.predicted_per_second is validated: a finite positive value is usable after successful attempt finalization, otherwise the native terminal rate is unavailable and fallback remains eligible. With more than one terminal timing observed in one attempt, the whole-attempt native rate is ambiguous regardless of whether one, several, or none of those timings contain a valid rate, so no provider-native terminal rate is published and existing fallback behavior is retained. This is what prevents a multi-request attempt whose first terminal timing carries a zero or invalid predicted_per_second and whose second carries a valid one from publishing the second rate for the whole OpenCode attempt. There is no multi-step aggregation formula, no averaging of rates, no last-step substitution, and no parsing of the optional usage metrics to support a future aggregation; predicted_n is a full completion count including first emissions and cannot be substituted either. Zero, missing, or non-finite predicted_per_second means unavailable, never 0 tok/s.

Final timings arrive before the SDK stream is guaranteed to finish. Caching then publishing at the provider source's finalize prevents a later stream error from leaving false terminal success. Discard closes the collector and suppresses late raw callbacks. Because beginAttemptTelemetry disposes provider before fallback, accepted native terminal rate sets providerDecodeAccepted before fallback finalization; the shared bridge's second check prevents late fallback overwrite.

**Alternatives considered**: A multi-step aggregation formula over usage metrics; last-step terminal rate; averaging step rates; combining incompatible predicted_n and predicted_ms; publishing final rate immediately on raw finish-reason chunk; carrying a previous retry's terminal state. Each would misrepresent attempt semantics or build infrastructure the current pinned checkout does not need.
