# Implementation Plan: Splash Generation Telemetry

**Branch**: 002-splash-telemetry (Spec Kit feature; current checkout branch: dev) | **Date**: 2026-09-28 | **Spec**: [spec.md](spec.md)

**Input**: Opt-in, request-scoped Splash telemetry through the existing generation telemetry path. This is a planning step; production code, tests, generated SDKs, and UI remain untouched.

## Summary

For Splash 1.1.0 served through the pinned OpenAI-compatible SDK, observe Splash-native metadata already present on the existing generation stream. Enable AI SDK raw chunks only for opted-in Splash requests and inspect them on the same fullStream before LLMAISDK.toLLMEvents. splashTelemetry: true is the explicit OpenCode-local opt-in and its only meaning is: observe Splash-native metadata on the existing stream, enable includeRawChunks as needed, parse request-local Splash prompt_progress when such chunks are present, parse the final Splash timings, and publish through the existing attempt-scoped session.telemetry path. It never modifies the inference request: return_progress is a real Splash protocol/request option, not this control, and it reaches the wire only through ordinary provider/request configuration. Normalize validated prompt_progress and a successful terminal timing through the existing attempt owner and session.telemetry publication path. Keep the generic fallback active during live decode because this Splash version has no request-local live decode rate. Accept a positive finite native final rate only after successful stream completion; then suppress fallback with the existing shared EffectBridge ordering. Telemetry never selects a different transport or runtime from the one generation would otherwise use. Keep MLX /events, generic fallback, event schema, store, helpers, and rendering behavior.

## Design and ownership

Choose splashTelemetry: true as the explicit opt-in after comparing the only existing backend-only telemetry control, mlxTelemetry: true. There is no generic telemetry-control seam in this checkout. Require the selected model to use @ai-sdk/openai-compatible before observing raw. Telemetry never selects a different transport or runtime from the one generation would otherwise use: if the already-selected generation path does not expose the required raw stream data, native Splash telemetry is unavailable and existing fallback behavior remains. The experimental native runtime can claim provider IDs openai/opencode/anthropic with a compatible SDK package, so an opted-in Splash model may land on native; that selection stands, and this feature does not redirect it. For the normal `splash` provider using @ai-sdk/openai-compatible the AI SDK/raw-stream design is retained because that is already its normal path. If mlxTelemetry is also enabled, retain the existing MLX source selection and do not attach Splash: the current attempt owner has one provider-source slot. Strip splashTelemetry from the SDK constructor copy in provider.ts before the cache key/factory and from prepared request options in llm.ts before ProviderTransform.providerOptions or native-runtime construction. mlxTelemetry remains untouched. return_progress is a real Splash protocol/request option, not the OpenCode telemetry-control flag: splashTelemetry never inserts it.

The observer sees each raw part in the same result.fullStream consumed by toLLMEvents. Enabling includeRawChunks is part of the opt-in and changes no request field; it applies only on the already-selected AI SDK path. The observer catches all parse/publication errors, does not await transport or telemetry work, and returns each original SDK part to the existing adapter unchanged. Copilot's raw billing handling remains in toLLMEvents; unrelated providers keep includeRawChunks off unless already enabled for Copilot.

The opt-in changes only what is observed, never what is requested. If the normal Splash request already contains return_progress: true through ordinary provider/request configuration, the passive observer consumes the resulting prompt_progress chunks. If it is absent, native Splash prefill progress is simply unavailable: live decode continues to use the existing OpenCode fallback, and the final Splash timings may still provide an authoritative terminal decode rate. If a backend rejects a provider-configured return_progress at request validation, the model request fails normally as a provider configuration matter; silently replaying it without the field would create a second inference request and is outside this feature. No retry without return_progress, no second inference request, and no polling are designed here. A fake-server case must make the boundary explicit during implementation.

Validate prompt_progress as a coherent, finite, nonnegative processed count no greater than positive total; cache is an initial cached count, and time_ms is an observation elapsed time, not ETA. Reject repeated/regressing progress, suppress unchanged displayed percentages, and publish advancing progress at most once per 250 ms with a final prefill flush when appropriate. Publish only current request progress as prefill. Absence of prompt_progress frames is harmless: no native prefill progress is published and live decode continues on the existing fallback. Do not set providerDecodeAccepted for prefill.

Cache the final Splash timings per provider request within the attempt, and count every recognized Splash terminal timing observation before any rate validation. A terminal timing is counted as soon as it is recognized; predicted_per_second is validated only after the count is known. A valid terminal rate is a finite positive predicted_per_second. Its interval excludes the first emitted batch, per Splash. Zero, missing, malformed, or non-finite values mean unavailable, never 0 tok/s, and leave fallback eligible. Do not publish the terminal rate as done until the underlying stream succeeds and attempt.finalize runs. With zero terminal timings observed, the native terminal rate is unavailable and fallback remains eligible. With exactly one terminal timing observed, its predicted_per_second is validated: a finite positive value may become the authoritative terminal rate after successful attempt finalization, otherwise the native terminal rate is unavailable and fallback remains eligible. With more than one terminal timing observed in one OpenCode telemetry attempt, the whole-attempt native rate is ambiguous regardless of whether one, several, or none of those timings contain a valid rate, so no provider-native terminal rate is published and the existing fallback behavior is retained. The collector increments the timing count for every recognized terminal timing before rate validation, so a second observed timing always fails closed. Do not average rates, do not use only the last step, and do not build multi-step aggregation infrastructure; optional usage metrics are not parsed to support future aggregation. If the fallback itself had no measurable interval/tokens, show no rate; never fabricate 0 tok/s.

The current streamText call has no stopWhen and the installed default is stepCountIs(1), so one successful provider step/timing belongs to each llm.stream attempt. Tool calls are events within that step; OpenCode's outer loop can create a later AssistantMessage for subsequent work. SDK retries before doStream yields a stream do not contribute raw timing; processor retries a failed llm.stream under the same AssistantMessage but creates a fresh attempt and reset. The Splash collector still stays step-aware: reset prefill context on start-step rather than summing prompt counts across requests, and count every recognized terminal timing observation before rate validation so a second observed timing fails closed to the fallback regardless of whether either timing contains a valid rate, rather than being aggregated, averaged, or taken as the last step.

The shared EffectBridge remains the publication ordering boundary. On valid terminal acceptance, set providerDecodeAccepted before enqueueing the provider event; fallback's execution-time check drops a late queued publication. On abort, setup failure, stream failure, discard, or superseded retry, discard the cached terminal and pending progress. On success, finalize provider before fallback through beginAttemptTelemetry. The source must ignore all late raw parts after closure.

6. Add end-to-end fake stream tests for fallback arbitration, terminal replacement, zero/missing/malformed/non-finite and more-than-one terminal timing, passive prompt_progress when independently present and its harmless absence, request-body equality with the opt-in on versus off, identical generation runtime selection with the opt-in on versus off, retry, abort, setup and stream failures, late parts, concurrency, and tool semantics.
7. Run existing MLX, fallback, provider, app reducer, and generation-telemetry UI regressions plus typecheck. Use live Splash only as optional smoke verification.
