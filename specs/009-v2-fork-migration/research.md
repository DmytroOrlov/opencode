# V2 Migration Research

**Feature**: `009-v2-fork-migration`  
**Evidence base**: paused rebase onto `5caf1f9f6f` and original commits `af1531f1a8`, `35dd5f2fc6`, `a0c8c7e123`, `af9515d01a`; V2 source at the rebase target; accepted `spec.md`; historical specs 001–008 where relevant. Inspection was read-only. No index or source changes were made as part of Plan.

## Decision summary

| Question | Classification | Decision from evidence |
|---|---|---|
| Does each old feature have a direct V2 file equivalent? | Resolved from source | No. Port behavior to the current V2 owner listed below; Git rename suggestions do not define ownership. |
| Where is TLS initialized? | Resolved from source plus safe implementation choice | CLI-owned pre-import bootstrap, before the statically imported command graph can perform TLS work, invokes a shared effective-CA verifier/attestation module exported through `@opencode/util`. Only actual verification of the effective trust set creates process-local attestation. If a supported runtime cannot establish this before network work, that path is HOLD. |
| Which entrypoints need TLS coverage? | Resolved from callers | Ordinary CLI command startup, `serve`, service re-exec, standalone/stdio, and their child processes. Cover development and built Bun and Node launch paths, including `packages/cli/vite.node.config.ts` and `packages/cli/script/build-node.ts`. |
| How is verified CA mode reported? | Resolved from current V2 contract | Optional `tlsCaMode` on V2 `ServerInfo` at `/api/info`, populated only from shared-verifier process-local attestation; a `ServerOptions` mode string alone is not evidence. App health exposes `bundled`, `system`, or `unknown`; current shell titlebar renders it. |
| Does the migration require a new compaction restart reconciler? | Resolved by accepted spec | No. Preserve existing orphan-running-to-failed handling. FR-024's optional reconciliation is not a new implementation requirement. |
| Does FR-030 match original Splash adaptation? | Resolved from original code/test | Yes. Its thresholds, samples, eligibility, origin check, explicit timeout precedence, and request-local behavior match. No spec correction is needed. |
| Is any product choice blocking Plan? | Resolved from available evidence | No. No genuine HOLD is required for the design. Runtime support must still be demonstrated during implementation; inability to prove TLS policy on a supported runtime is an explicit HOLD condition, not an open product choice. |

## V2 ownership and behavior evidence

### TLS CA security and startup — `af1531f1a8`

**Original behavior.** The change adds strict CA mode parsing, a bundled default and explicit system mode, rejects contradictory/invalid options, controls ambient runtime trust configuration, verifies the effective trust sources, protects certificate verification, carries policy across child processes, and reports mode to health and the titlebar. Its probes and tests live under V1 `packages/opencode` and the former app titlebar/health path.

**Actual V2 path.** `packages/cli/src/index.ts` is the command entry and statically loads much of the CLI graph before `ensurePluginRuntime()` and command dispatch. A statement added after imports is too late to establish the strict pre-network guarantee. The executable therefore needs a CLI-owned shim that initializes policy and dynamically imports the existing command graph. `packages/cli/src/commands/handlers/serve.ts` enters `packages/cli/src/server-process.ts`, which dynamically loads `@opencode/server/process`; that calls `packages/server/src/process.ts::start`, which currently binds/listens before serving routes. Self-reexec is in `packages/cli/src/util/process.ts`; service and standalone launchers are in `packages/cli/src/services/service-config.ts` and `services/standalone.ts`. The Node build path includes `packages/cli/script/build.ts`, `packages/cli/vite.node.config.ts`, `packages/cli/script/build-node.ts`, and `packages/cli/src/node/target.ts`. The launcher must cover these actual outputs. On Node self-re-exec, replace only the CA flag and retain non-CA runtime flags such as `--experimental-ffi` and warning settings. V2 currently injects `--use-system-ca` in build/target configuration and forwards it in the self-command path, which conflicts with a bundled default unless selection occurs before launching the built runtime.

**Contract path.** A shared low-level effective-CA verifier/attestation module under `packages/util`, exported through `@opencode/util`, is imported by both CLI and Server. The CLI bootstrap invokes actual trust-set verification before loading the command graph; `ServerProcess.start` requires process-local attestation before binding/listening. A `ServerOptions` mode string is not trusted evidence. `packages/protocol/src/groups/server.ts` owns the `ServerInfo` HTTP schema; `packages/server/src/handlers/server.ts` and `packages/server/src/server-info.ts` supply `/api/info`. `packages/app/src/runtime/server/health.ts` requests `server.info()` and keeps the per-connection health record. `packages/app/src/shell/titlebar/titlebar.tsx` renders the active server status and has a current right-side titlebar slot. The CA badge therefore consumes that health record; it must not create a parallel probe or infer mode from the endpoint.

**Reuse / missing / do not port.** Reuse the CLI lifecycle, child process helpers, ServerInfo endpoint, app health cache and titlebar shell. Missing behavior is early policy selection/verification, safe mode propagation, a shared `@opencode/util` effective-trust verifier that alone establishes process-local attestation, a `ServerProcess.start` precondition that rejects absent/unverified attestation, an optional verified health field, and the badge. A mode string in `ServerOptions` cannot pass that precondition. A direct supported server host must perform actual verification through the shared module or fail before bind. Keep old `packages/opencode`, `/global/health`, old app component paths, old SDK-generated files, and old test helper deleted. Do not place process bootstrap under `packages/core`: Core does not own the executable boundary.

**Risk and discriminator tests.** Static imports can precede runtime statements in `cli/src/index.ts`; adding verification below those imports does not establish “before network.” `--use-system-ca` on the current built path may override bundled selection. Hostile `BUN_OPTIONS`/`NODE_OPTIONS` can alter trust unless parsed/sanitized at the executable boundary; over-sanitizing Node args can also drop required `--experimental-ffi` or warning settings. Port the controlled CA fixtures and assert actual TLS request results as well as environment/argv. Cover Bun and Node built artifacts in both modes, `packages/server/test/process.test.ts` with valid and forged/unverified state, its `test/fixture/server.ts` setup, and app health/shell tests.

### Safe generation recovery and fallback — `af9515d01a`

**Original behavior.** The integrated change distinguishes retry scheduling from the later retry/failover decision, observes fallback changes made during backoff, prevents replay of settled or uncertain tool work, keeps cancellation terminal, uses shared generation admission to coordinate global config replacement, retains request-scope-independent prompt work, and fixes cancellation of a runner parked on an admitted run. It also protects updates across distinct runtime config graphs.

**Actual V2 path.** `packages/core/src/session/session.ts` durably admits prompts through `SessionInbox` before waking execution; HTTP scope closure does not own accepted work. `packages/core/src/session/execution.ts` routes process-global, Session-ID-based work to a local runner. `packages/core/src/session/run-coordinator.ts` owns local fibers, coalescing, interruption and settling. `packages/core/src/session/runner/llm.ts` drains work; `runner/step.ts` owns the physical attempt/tool settlement boundary; `runner/retry.ts` currently schedules waits and retry limits. These are distinct responsibilities: a scheduled wake is not authority to retry the same primary model.

Config lives in `packages/core/src/config.ts` as a `makeLocationNode` service with per-location update serialization. `Config.update` currently writes the shell config and requests reload, but before Stage 3 T028 its existing success response can occur without persisting the newly introduced fallback field. `packages/schema/src/config.ts` has the public config shape and `packages/protocol/src/groups/config.ts` exposes an experimental config patch route, but the app sync path in `packages/app/src/runtime/server/sync.tsx` still reports config update as unavailable. There is no V2 fallback field, runtime fallback intent or shared generation admission service. The active fallback field and update route are therefore genuine V2 additions, not code that should be hidden in the old config implementation; no app fallback update may be sent until the Stage 3 contract and durable persistence sequence through T028 is complete.

**Parked runner boundary.** The old regression exercises an admitted runner interrupted while waiting behind protected work. Its V2 equivalent is the execution chain joining `SessionExecution` / `RunCoordinator` to the agent/subagent operation in `packages/core/src/tool/plugin/subagent.ts`, including the child job wait and interruption handler in `packages/core/src/session/subagent-job.ts`. Adapt the test to cancel the actual parked operation and assert settlement, exactly-once lease release, and progress of the next protected owner. Keep V2's existing behavior that cancelling a joined waiter does not cancel the shared owner.

**Reuse / missing / do not port.** Reuse durable prompt admission, Session-ID execution, process-local coordinators, write-ahead claim semantics, and existing retry limits. Add only the shared admission/config revision mechanism needed for the accepted cross-runtime guarantee. Do not transplant V1 `Effect.Runner`, `GenerationGate`, old processor loop, or old provider orchestration. Do not conflate the shared admission lease with the existing DB execution claim. FR-024's optional restart reconciliation is expressly out of implementation scope.

**Risk and discriminator tests.** An interrupted operation parked on admission can hang if its acquire/wait is masked or cleanup does not own a lease yet. A fallback change after retry scheduling can be ignored if retry code decides the model before sleeping. A failure after a tool began has an unknown outcome and cannot be treated as clean replay. Runtime intent can be lost if config update rollback uses a stale snapshot or a failure clears a newer revision. Test `session-run-coordinator.test.ts`, `session-execution.test.ts`, `session-runner.test.ts`, `session-runner-retry.test.ts`, `tool-subagent.test.ts`, and config tests with two distinct runtime graphs.

### Crash-safe compaction and session history — `af9515d01a`

**Actual V2 path.** `packages/core/src/session/compaction.ts` owns summary/native compaction. Durable facts are declared in `packages/schema/src/session-event.ts`; typed projected variants are in `packages/schema/src/session-message.ts`; `packages/core/src/session/message-updater.ts` projects `Compaction.Started`, `Ended`, and `Failed`; `packages/core/src/session/history.ts` selects the latest completed compaction; `packages/core/src/session/projector.ts` handles message projection and fork copying. `SessionMessageTable.data` in `packages/core/src/session/sql.ts` is typed JSON, so the design can add optional typed candidate/publication facts without a new table. `packages/core/src/bus.ts` persists accepted durable events and applies their projector changes in one SQLite transaction. Pending work is separate in `SessionInbox` and its enqueue/delivery projectors.

**Current behavior and gap.** V2 records started/ended/failed states and settles orphan `running` compactions as failed on a later drain. However, `Ended` currently creates a completed projection that history may treat as authoritative. It does not separate “summary generated” from “summary published.” The projection path can also append a completion when a matching running row is absent, which is unsafe for stale completion after delete. Current fork projection remaps copied message row IDs, but a new compaction publication contract must remap its own exact references too.

**Minimum native change.** Give each new candidate an explicit identity, persist successful content as a candidate, then publish it with a distinct durable decision bound to the exact candidate. Transactional validation must reject mismatched, duplicate, deleted, incomplete, empty/unreadable, or cross-session references without partially persisting the event. History selects the prior published view until publication; model-visible history and pending inbox remain separate. New-format malformed records cannot drop into legacy rules. Keep strict legacy reading and existing orphan settlement; do not add a startup reconciler.

**Risk and discriminator tests.** A final conversation that looks plausible does not prove pending work survived. Test every boundary before and after publication, rejected projector mutation atomicity, deletion followed by stale completion/extra parts/replay/restart, both full and tailed summary reader validation, legacy full/tailed/chained/failed behavior, inbox visibility, and fork-owned references. Existing focused owners are `session-compaction.test.ts`, `session-native-compaction.test.ts`, `session-projector.test.ts`, `session-runner.test.ts`, and session creation/fork tests.

### Transport liveness — `af9515d01a`

**Actual V2 path and reusable behavior.** `packages/ai/src/route/transport/http.ts` owns response header and stream read timeouts. It measures each pending chunk read through `Stream.timeoutOrElse`; `http.timeout` remains infinite when not set. `packages/ai/src/schema/options.ts` provides the generic 300,000 ms header/chunk defaults. The inspected V2 provider-settings resolution does not currently apply the original provider-specific 150,000 ms `opencode-go` chunk default; that default must be ported through `packages/core/src/model-resolver.ts`, with explicit numeric or `false` `chunkTimeout` taking precedence. Keep the generic default for other providers and the V2 per-read implementation, which avoids a total-generation timeout by default.

**Original adaptation comparison.** The original implementation is in V1 provider code and tests: opt-in local Splash, five successful nonempty reads each waiting at least 100 ms, discard the longest, use ten times the largest of the remaining four, clamp at 30,000 ms and the provider timeout; apply to later reads, request-local; only if the effective endpoint is loopback HTTP(S) and the actual request URL has the configured endpoint origin. Any explicit `chunkTimeout` including `false` bypasses adaptation; header/total settings are unchanged; each retry/compaction request starts fresh. FR-030 and its neighboring requirements state these constraints accurately. No correction is needed.

**Minimum V2 change.** Resolve the `opencode-go` 150,000 ms chunk default through actual provider settings while retaining the generic 300,000 ms default and allowing explicit numeric/`false` overrides to win. Put Splash calibration at the AI response-reader boundary where actual read waits are observed. Eligibility must use explicit opt-in and resolved endpoint plus actual URL origin; provider name/host/port alone cannot authorize. Preserve existing `TransportError` retry classification and abort cancellation. Do not add an independent retry policy or enable adaptation by default. Cover defaults/precedence in focused model-resolver and fake-reader tests in `packages/ai/test/http-timeout.test.ts`; GPU validation is not required.

### Attempt-scoped telemetry — `35dd5f2fc6`

**Original behavior.** The original commit created an attempt-owned lifecycle with exact attribution even when assistant ID is reused; MLX compatibility; opt-in Splash support; native-versus-estimated provenance; no zero fabricated for missing values; strict semantic validity; no polling/inference-request or runtime change; bounded provider listeners; failed/aborted attempt discard; and generation success independent from telemetry success. Its V1 event/UI path was schema telemetry → app global sync → session UI generation telemetry.

**Actual V2 path.** V2 exposes normalized `LLMEvent` in `packages/ai/src/schema/events.ts`; one request is streamed through `packages/ai/src/route/client.ts`; `packages/core/src/session/runner/step.ts` owns one physical attempt. `runner/llm.ts` can retry while reusing assistant message identity. Provider frames are decoded by adapters such as `packages/ai/src/protocols/openai-chat.ts`; raw response frames are not a general durable V2 event. Typed `mlxTelemetry`/`splashTelemetry` provider settings must resolve through `packages/core/src/model-resolver.ts` and be stripped by `Provider.CORE_KEYS` and `packages/core/src/aisdk.ts::prepareOptions` before dispatch. V2 has no attempt telemetry lifecycle, event, store, or session UI presentation in the inspected Core/AI/schema/app paths.

**Minimum native change.** Keep attribution, source arbitration, accepted-value state, publication, cancellation, and cleanup in `SessionStep.attempt`; AI adapters observe provider protocol only and never carry session identity. Capture effective endpoint and Redacted `route.auth` from `SessionModelRequest.Prepared` after request hooks, and never leak credentials to event payloads or diagnostics. Accept an observation synchronously before asynchronous publication. Preserve MLX behavior and add opt-in Splash without changing inference options or implicitly enabling `return_progress`; prefer MLX over Splash for equivalent native metrics and validate terminal-rate observations before publication. Send one ephemeral attempt-tagged session event and use V2 session event/reducer/timeline ownership; no telemetry in durable conversation history. Reject stale events by attempt ID and suppress telemetry exceptions at the observation boundary.

**Risk and discriminator tests.** Session/message identity is insufficient if a retry reuses it. Native and estimated values cannot be merged based only on arrival order; malformed or aggregate values and prefill-only signals cannot be promoted to decode authority. Watchers must release on all exits, while Redacted credentials must not enter events or diagnostics. Focus Core option-stripping and lifecycle/attribution tests, AI observer cleanup/frame parsing, and app reducer presentation tests. Do not require a live MLX/GPU service or expand the whole suite.

### Composer selection — `a0c8c7e123`

**Original behavior.** This commit is a compact-control presentation change in V1 prompt inputs; it is not an independent persistence or backend design. The pair behavior and stale-update guarantees come from the historical model-pair/config features and accepted feature requirements.

**Actual V2 path.** The composer is `packages/app/src/composer/composer.tsx` and `composer/editor/editor.tsx`; model selection state is in `packages/app/src/providers/models/selection.tsx`; model catalog and variants are in `providers/models/select-dialog.tsx` and `providers/models/models.tsx`. Existing-session composition uses the session composer region/controller/adapters. New-session flow uses `new-session/composer-adapter.ts` and promotion. Primary selection and variant are persisted through V2 session/workspace model-selection storage and reconciled from server acknowledgement. Global config is server-owned, but fallback is absent from `Config.Info` and `Config.Patch`; `runtime/server/sync.tsx` has an unavailable-config-update branch. The active V2 model/agent/variant selector triggers do not yet have the incoming `!px-0` override, so that compact styling is the only change to carry in Stage 2. Fallback schema, client, persistence, and UI behavior are Stage 3 tasks; no UI fallback request may be sent before T028 because the current V2 update response is not durable confirmation.

**Minimum native change.** Stage 2 applies only compact trigger padding in the active V2 composer and does not add pair selection. In Stage 3, keep primary selection and variant with the current V2 owner; implement fallback in the existing global config contract and durable update flow, not an app-local duplicate pair. Complete `Config.Info`/`Config.Patch`, generated client, backend runtime intent, and backend persistence before the app sends fallback updates. Applying a fallback-only patch with `shell` omitted must preserve the configured shell. Then make a pair action one client intent with model-associated variants; server acknowledgement/failure and async responses must be revision-aware so stale rollback cannot replace newer intent. Reuse draft promotion and session flows, with global fallback unchanged across new session creation. Carry the locale key across each supported locale as required by FR-045.

**Risk and discriminator tests.** Config fallback is not currently publicly writable through the app API, so Stage 2's compact styling is intentionally not a functional pair feature. Variant state can be incorrectly left on the other model after swap. New-session draft state can accidentally reset a global fallback. Exercise existing and new-session flows, delayed failure, fallback absent from visible catalog, variant compatibility, locale parity, and preservation of an existing shell value during fallback-only PATCH in the ordered Stage 3 tests.
