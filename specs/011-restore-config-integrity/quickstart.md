# Validation guide

Run from repository root with the checkout's Bun dependencies installed. Core's test script supplies an isolated home and temporary directories. Use deterministic barriers/injected failures, not sleeps or external providers. Run each slice's bounded commands in [plan.md](plan.md); S1 and S2 require only their listed core checks, and S3 runs its scoped server/client/app checks and generated/type checks. Record commands, exit status, injected-boundary evidence and any unrun checks; do not weaken existing assertions.

1. S1: real JSONC fixture with valid, invalid, no-op, temporary-write and rename cases; inject real reload/notification/cleanup boundaries and prove reached state, bytes, reader coherence or degradation, reconciliation and resource release. Before rename retain old; after rename but before publication report unpublished; after publication report a distinct mandatory-completion failure only for a real boundary, or record optional-housekeeping diagnostics and succeed.
2. S2: hold a shared generation lease, reserve B then C, force C validation first, observe C before release, and exercise B/C/D success, failure and cancellation permutations. Verify ordered sparse persistence, restart state and lease progress. Hold retry backoff, change intent or committed fallback, and verify next physical dispatch and immutable prior attempt with tool safety.
3. S3: exercise actual route and both generated clients for 204, precommit, unpublished and generic errors, optional-housekeeping diagnostics, and any real mandatory postpublication failure. Prove each identity appears only at its actual boundary and is structurally decoded by both clients when applicable; verify generic 500, caller compensation, settings and no false rollback. Complete the deterministic config → admission → recovery → route/client trace.

`check:generated` runs generation and compares generated files; use it only during implementation after intended generated artifacts are updated. The plan does not run generation. See [contract](contracts/config-update.md) for expected payload and [data model](data-model.md) for state distinctions.
