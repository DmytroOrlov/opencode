# Feature Specification: Restore Config Integrity and Fallback Ordering

**Feature Branch**: Not created (specification-only work)

**Created**: 2026-11-20

**Status**: Draft

**Input**: Focused remediation of the V1 guarantees already required by `009-v2-fork-migration` for global configuration replacement and runtime fallback ordering.

## Clarifications

### Session 2026-11-20

- Q: Should a recovery attempt that has not yet been dispatched use the latest eligible effective fallback, while each dispatched attempt keeps its original model and variant attribution? → A: Yes. A pending recovery attempt uses the latest eligible effective fallback; each dispatched attempt retains its model and variant, and recovery never replays uncertain external tool effects.
- Q: When replacement commits the file but runtime publication fails, how should the PATCH caller learn the outcome? → A: Return a machine-readable committed-but-degraded error, with protected readers blocked or explicitly degraded until reconciliation. An intentional, endpoint-specific HTTP 500 error-contract evolution is authorized, including protocol and generated Promise/Effect client changes; preserve caller behavior and document any changed error type rather than assume exact error-shape compatibility.
- Q: If two concurrent patches begin validation in order B then C, but C finishes validation first, which order must determine their commits? → A: Order commits by entry into the update owner. Late validation of B cannot overwrite newer accepted C intent; invalid or cancelled updates release their position without blocking later commits.

### Publication-state reconciliation 2026-11-20

Outcome depends on actual commit, coherent publication and completion state, not on the name or ordering of a throwing operation. The PATCH-specific evolution includes both committed identities below where their real boundaries exist.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Reliable configuration updates (Priority: P1)

As a user changing global settings, I need an update to commit a complete, valid configuration and publish it coherently, with a truthful outcome if any stage fails, so that an interrupted or unsuccessful save cannot damage my settings.

**Why this priority**: A failed save can otherwise corrupt settings used by later requests and processes.

**Independent Test**: Exercise the production V2 update owner with a real temporary configuration and controlled validation, temporary-write, replacement, and post-replacement publication failures; compare file contents, permissions, reader state, and reported outcome before and after each operation.

**Acceptance Scenarios**:

1. **Given** an existing valid document and committed readers, **When** a patch would make the complete document invalid, **Then** the update fails and the file and committed readers remain unchanged; a valid equivalent update succeeds.
2. **Given** a valid changed document, **When** an injected temporary-write failure reaches that boundary, **Then** the update reports failure, the original file and committed readers remain intact, and no temporary file remains; a retry without the failure succeeds.
3. **Given** a complete temporary document, **When** an injected atomic-replacement failure reaches that boundary, **Then** the operation reports failure, preserves the original file and committed cache, and removes temporary files; a successful replacement exposes the new committed state.
4. **Given** an existing JSONC document with comments, supported formatting, unrelated properties, and file permissions, **When** a valid changed patch succeeds, **Then** subsequent readers see the complete new configuration, existing permissions and unrelated properties remain, and comments and formatting are preserved where supported.
5. **Given** a patch whose candidate equals the latest committed document at its serialized commit boundary, **When** it is applied, **Then** it succeeds without a filesystem write, replacement, or unnecessary invalidation and leaves no stale intent; a changed candidate replaces and publishes the committed state.
6. **Given** respectively an omitted fallback patch, an explicit null, and a legacy document with no fallback, **When** updates and reads occur, **Then** omission leaves the existing value untouched, null explicitly disables fallback, and legacy absence retains the existing undefined default (`mlx/qwen3.8-27b`, `xhigh`); none is silently converted into another state.
7. **Given** a pre-rename failure, **Then** the old document remains and neither committed-state identity appears. **Given** rename succeeds but coherent publication has not, **Then** PATCH returns HTTP 500 `CONFIG_COMMITTED_BUT_UNPUBLISHED`, the new file remains committed and protected readers are blocked or explicitly degraded until reconciliation. **Given** coherent publication succeeds but a real mandatory completion operation fails and success is impossible, **Then** PATCH returns HTTP 500 `CONFIG_COMMITTED_WITH_POSTPUBLICATION_FAILURE`, retaining the committed and published state. Do not create an artificial failure path. **Given** optional housekeeping fails after publication without compromising completion, **Then** record a diagnostic, release required resources and admission, and return HTTP 204. Deterministic boundary-reached tests distinguish both identities from ordinary generic failures, exercise both generated clients where the corresponding real boundary exists, preserve composer compensation and settings handling, and never assume a committed failure rolled back. Document intentional client error-type changes.

### User Story 2 - Latest accepted recovery intent (Priority: P1)

As a user changing fallback while generation is active, I need recovery to see my newest valid accepted choice promptly, while saves remain ordered and failed saves are reported honestly.

**Why this priority**: A queued save must not leave recovery using an older choice or allow a stale write to become the final durable setting.

**Independent Test**: Use deterministic barriers in the actual V2 configuration, admission, and recovery paths to hold generation and coordinate two accepted updates, then release admission and observe runtime and committed outcomes.

**Acceptance Scenarios**:

1. **Given** generation A holds a shared admission lease, **When** valid update B stages fallback B and waits for exclusive admission, and valid update C is accepted while B is still waiting, **Then** recovery observes C before either update commits; neither B nor the old committed value replaces C as the latest accepted intent.
2. **Given** that trace, **When** B completes, fails, or is cancelled in separate controlled runs, **Then** B's cleanup cannot erase or roll back C; failure or cancellation is reported rather than represented as B's durable success.
3. **Given** B and C are accepted in that order and both settle successfully after A releases admission, **When** the final committed configuration is read, **Then** it contains C, not B, and both writers make progress.
4. **Given** an accepted runtime intent whose persistence fails or is abandoned, **When** a new process starts, **Then** it reads the last successful durable commit, not the abandoned intent; a successful later commit is visible after restart.
5. **Given** recovery is waiting in backoff, **When** a newer eligible fallback is accepted before the next dispatch, **Then** the next decision uses that latest eligible selection immediately before dispatch and does not dispatch an unnecessary primary attempt. **Given** a model and variant have already been dispatched, **When** intent changes, **Then** that attempt retains its original pair and only a later decision can use the new one.
6. **Given** a writer queued behind a shared lease, **When** it is interrupted before commit, **Then** it releases its reservation, leaves the file unchanged, and does not prevent a later writer from progressing after release. Once the protected atomic commit boundary is crossed, cancellation completes or cleans up forward without partial committed state.
7. **Given** a patch omits fallback, **When** accepted, **Then** it stages no fallback override; an explicit null stages a clear visible to recovery without being mistaken for omission. Invalid fallback validation publishes no intent; cancellation after staging performs revision-safe cleanup, and staging alone is neither a durable commit nor an HTTP success.

8. **Given** B commits successfully and newer C stages an intent, **When** C fails or is cancelled before commit and remains current, **Then** cleanup removes C and recovery observes committed B, not C or an older request-start fallback. If newer D is staged before C cleanup, C cannot erase D. If B fails or is cancelled and C succeeds, C becomes the durable value; if B succeeds and C fails, B remains durable and C reports failure.
9. **Given** concurrent accepted sparse patches B and C change fallback and `shell` respectively, **When** they commit in update-owner entry order, **Then** both changes survive and neither overwrites the other from a stale snapshot. **Given** durable fallback A, B stages B and C stages A while admission is blocked, **When** admission is released, **Then** B commits B followed by C committing A; C is not discarded as a no-op against the original A.
10. **Given** a fallback update has committed and its staged intent has cleared, **When** a pending retry finishes backoff and reaches its next decision, **Then** it uses the latest eligible effective committed fallback, not an older recorded request-start fallback; an already dispatched attempt retains its model and variant.
11. **Given** B enters the update owner before C but C validates and stages first, **When** B validates later, **Then** B cannot replace C as current intent, and successful commits occur B then C. If B is invalid or cancelled, its position is released and C can commit.

### Edge Cases

- Invalid model or variant is rejected before its fallback intent becomes visible; valid acceptance is distinguishable from durable commit.
- Older failure, cancellation, or completion after a newer acceptance cannot clear that newer revision. A failed latest revision may be removed or reverted only if it is still current.
- Separate configuration runtime graphs share admission; active generation remains protected from destructive replacement. Lease release is exactly once on completion, failure, or cancellation.
- Before successful replacement, failure leaves the old file and committed readers intact. Successful replacement commits the new document; subsequent publication or cleanup failure cannot undo or disguise that outcome. Before new protected readers proceed, publication must succeed or explicit degraded-state handling must prevent stale reads. No power-loss durability beyond the filesystem contract is promised.
- Sparse patches are applied to the latest committed document at their serialized boundary; legacy undefined, explicit null, and selected fallback remain distinct. Eligibility and already-attempted-model restrictions remain in force.
- A pending recovery attempt uses the latest eligible effective fallback, while each dispatched attempt retains its model and variant attribution and uncertain external tool effects are never replayed, consistent with 010 FR-025.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The V2 Config owner MUST validate the complete resulting document before committing a changed global configuration; invalid results MUST leave the prior file and committed readers unchanged.
- **FR-002**: Changed content MUST be written to a unique temporary file in the target directory and atomically replace the target, preserving existing permissions. Any failure before replacement MUST preserve the old target and committed reader state and clean up temporary files.
- **FR-003**: Successful atomic replacement commits the new document. Before exclusive admission is released, relevant committed readers MUST observe it or forward reconciliation or explicit degraded-state handling MUST prevent stale protected reads. Coherent publication and all mandatory completion are required for success; failure of optional housekeeping after publication is diagnostic and does not prevent success or strand required resources or leases. Classify each operation by its actual role and state, not its name. Compare each candidate with the latest committed document at its serialized boundary; a true no-op MUST perform no write, replacement, or unnecessary invalidation and MUST clear its own still-current intent safely.
- **FR-004**: Updates MUST retain JSONC comments and supported formatting, unrelated properties, and sparse patch semantics. Omitted fallback means no change; explicit null means clear; legacy undefined retains the existing default.
- **FR-005**: Before rename, failure retains the old document and carries neither committed-state identity. After rename and before coherent publication, return endpoint-specific HTTP 500 `CONFIG_COMMITTED_BUT_UNPUBLISHED`, retain the new file, and block or explicitly degrade protected readers until reconciliation. After coherent publication, a real mandatory completion failure that prevents success returns HTTP 500 `CONFIG_COMMITTED_WITH_POSTPUBLICATION_FAILURE`; do not invent such a production boundary. Optional housekeeping failure after coherent publication is recorded diagnostically and retains 204 when completion is otherwise successful, with no required resource or lease stranded. Unrelated generic defects carry neither identity; failures at the governed commit/publication boundaries are classified by actual state regardless of their underlying cause. Both identities MUST be structurally observable in generated Promise and Effect clients when the corresponding real boundary exists; deterministic wire, client and affected-caller regressions MUST prove the actual state, exclusive identity, ordinary generic 500 decoding and 204. Preserve composer compensation and settings behavior without representing committed outcomes as rollback. Document actual changed error types; exact error-shape compatibility is not assumed.
- **FR-006**: An explicit fallback selection or clear is accepted for runtime-intent purposes only after backend validation succeeds and its revision is staged, before exclusive admission is acquired or awaited. Validation failure MUST publish no intent. Acceptance alone is neither durable persistence nor HTTP success; cancellation after staging MUST invoke revision-safe cleanup. Omitted fallback MUST stage no override. Active recovery MUST observe the latest eligible accepted intent even while an older writer waits.
- **FR-007**: Updates MUST reserve commit order on entry into the update owner, before validation, and persist in that initiation order even if validation finishes out of order. Invalid or cancelled updates MUST release their position without blocking later commits. An older update completing validation late MUST NOT stage over a newer accepted fallback intent. Persisted updates remain serialized while newer intent stages early. Each sparse patch MUST be applied and compared against the latest committed document at its own serialized commit boundary so no stale snapshot loses another accepted change; an older accepted writer cannot overwrite a newer successfully settled writer as the final committed value. Failure or cancellation of B followed by C success leaves C committed; B success followed by precommit C failure leaves B committed, with each outcome reported independently. Cleanup MUST affect only its own still-current revision and MUST NOT erase or roll back a newer accepted revision.
- **FR-008**: A pending retry MUST choose the latest eligible effective fallback after backoff and immediately before dispatch, including a committed update whose staged intent has cleared, rather than an older request-start snapshot. Preserve model eligibility, already-attempted-model guards, retry caps, variant and tool-side-effect safety, pending-compaction behavior, and truthful request attribution; recovery MUST NOT replay uncertain external tool effects. Each physically dispatched attempt retains its resolved model and variant.
- **FR-009**: Runtime intent, committed configuration, and publication outcome MUST remain distinguishable. Effective fallback precedence is the latest valid still-active accepted intent, otherwise the latest successfully committed fallback, otherwise legacy/default resolution when the committed field is absent. Explicit null remains a clear. If newer C fails or is cancelled before commit, cleanup removes C only if current, exposing committed B rather than C or a request-start snapshot; cleanup cannot erase newer D. A newly started process MUST reconstruct from the last successful commit only.
- **FR-010**: The existing shared/exclusive admission service MUST protect active generation across runtime graphs. A queued writer MUST be interruptible without leaked reservations, file damage, or deadlock; cancellation after successful replacement MUST complete or clean up forward, preserving the committed outcome and reader coherence without partial state.
- **FR-011**: Preserve V2 Effect ownership, the Config owner, schema, protocol, generated client behavior, and working behavior outside this scope, except for the intentional endpoint-specific PATCH error-contract evolution authorized by FR-005. Preserve existing successful call behavior and affected callers’ failure handling, including composer compensation and settings updates, while accounting truthfully for committed unpublished and committed published failures and diagnostic-only housekeeping; document any intentional change to the previously thrown error type. Do not redesign global error handling, introduce a second authoritative fallback store, weaken request attribution, discard commit serialization, or restore the V1 subsystem. A generic transaction framework is excluded unless planning demonstrates existing owners cannot supply the required atomicity.
- **FR-012**: Acceptance evidence MUST preserve the failure modes ruled out by V1 assertions, not merely count passing V2 tests. Every guarantee MUST have a positive path and a decisive negative assertion; injected failures MUST prove they reached the intended write, replacement, publication, or admission boundary. Existing V2 assertions MUST NOT be weakened, skipped, or removed to obtain a pass.
- **FR-013**: Evidence MUST exercise actual V2 production paths in `packages/core/src/config.ts`, `packages/core/src/config/fallback-runtime-intent.ts`, `packages/core/src/session/generation-admission.ts`, `packages/core/src/session/runner/llm.ts`, and `packages/server/src/handlers/config.ts`, with deterministic synchronization barriers rather than arbitrary sleeps. Existing test owners are preferred; no new test file is required solely by this contract.
- **FR-014**: Any claimed impossibility MUST identify the exact blocking V2 boundary and place the affected contract on HOLD for an explicit contract decision; a limitation, reduced test, or prior completed task is not acceptance.

### Key Entities *(include if feature involves data)*

- **Committed configuration**: The last successfully replaced global document; reader publication is a separate state that may still be pending or degraded.
- **Fallback intent**: A backend-validated, process-local revision representing a selection or explicit clear, distinct from durable configuration.
- **Admission lease**: Shared protection for active generation or exclusive protection for a configuration commit, acquired and released by its owning operation.
- **Attempt snapshot**: The model and variant fixed for one dispatched generation attempt.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All seven Story 1 scenarios pass with intact prior content and reader state in every injected pre-replacement failure, and complete read-after-commit content on success.
- **SC-002**: All eleven Story 2 scenarios pass under controlled ordering, including each of B completion, failure, and cancellation; no older cleanup erases C and successful B then C leaves C durable.
- **SC-003**: Every restored guarantee has recorded positive and decisive negative evidence through the relevant production path, with each injected failure shown to reach its intended boundary and no reduction in existing V2 assertions.

Document any intentional change in the previously thrown error type; exact error-shape compatibility is not a condition. This decision does not establish implementation or behavioral acceptance.
- Broad recovery, compaction, SSE, telemetry, composer redesign, unrelated cleanup, live GPU, browser sweeps, Strobe benchmarks, and full repository regression are outside scope.
