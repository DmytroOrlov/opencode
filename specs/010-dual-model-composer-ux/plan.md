# Implementation Plan: Dual-model composer UX

**Branch**: `010-dual-model-composer-ux` | **Date**: 2026-11-18 | **Spec**: [specs/010-dual-model-composer-ux/spec.md](./spec.md)

**Input**: Feature specification from `specs/010-dual-model-composer-ux/spec.md` (FR-001…FR-037, SC-001…SC-014)

## Summary

Reorder the composer's model controls to **primary model → primary variant → fallback model → fallback variant**, delete the separate swap (`⇄`) and clear (`×`) affordances, and make the exchange happen automatically when a picker is used on the model already held in the other slot. Both slots keep their existing owners — the per-session/draft primary `ModelSelection` (session: `providers/models/selection.tsx`; draft: `createComposerModelSelection`) and the global `createFallbackModelSelection()` config owner — and the exchange lives on the wrapped slot objects built in `createComposerControls` (`packages/app/src/composer/selection.ts`), the only place that already sees both. The pair rule already exists (`swapModelPair`/`ComposerModelPair` in `packages/app/src/session/composer/selection.ts`, including "a variant must be offered by the model it lands on"), so the pair math is reused rather than re-designed. What the owners cannot provide on their own, and what this plan adds deliberately: one **non-durable** exchange phase (the pre-exchange pair plus an attempt token) so a late rejection can restore either half and cannot compensate over a newer selection, and two additive signals — the primary record write's failure (`persist.ts` already knows it at `:86`; `persistStore` must carry it out and `persisted()` must forward it) and a per-call failure callback on the fallback write (already supported by `fallbackUpdateState.save`). No new queue, no durable pair store, no transaction layer; the fallback's own serialized `pending` chain and the primary's own commit machine stay authoritative for their halves. Display-level collision handling (the fallback-inactive state) is the invariant that guarantees FR-008 for every write path, including the non-composer writers this change does not touch. One line changes in the core runner so recovery and the composer agree on model identity: provider + model, variant ignored.

## Technical Context

**Language/Version**: TypeScript (strict, `exactOptionalPropertyTypes`) in a Bun 1.4.4 workspace; SolidJS for UI, Effect for `packages/core`.

**Primary dependencies**: `solid-js` + `@solid-primitives/*` (composer, dialogs), `@kobalte/core` (`Menu`, used by `ComposerEditorSelect`), `@opencode/plugin`/`@opencode/schema`/`@opencode/client` (server SDK), `@playwright/test` (component + e2e), `bun:test`.

**Storage**: unchanged. Primary slot: the existing per-workspace `Persistence` session-selection records read/written by `LocalProvider` (`packages/app/src/providers/models/selection.tsx`). Fallback slot: the existing server config field `fallback`, written through `server.ctx.sync.updateConfig({ fallback })` → `PATCH /api/experimental/config` (`packages/app/src/runtime/server/sync.tsx:178`), read back by `loadGlobalConfigQuery` (`packages/app/src/runtime/server/global-sync/bootstrap.ts`). No schema or record-shape change anywhere.

**Testing**: `bun test` unit tests (pure state machines, `packages/core/test/session-runner.test.ts`), Playwright component tests (`packages/app/component-tests`), Playwright e2e against the mock server (`packages/app/e2e`, `e2e/utils/mock-server.ts`), and `test-browser/fixtures/model-selection.ts` for the browser-conditioned selection integration.

**Target platform**: `packages/app` web/desktop renderer (desktop Electron + browser, LTR and RTL, desktop ≥768px and phone <768px), plus `packages/core` session runner.

**Performance goals**: composer control row must not add layout or render work; the control row is measured by `packages/app/perf/composer.bench.ts` and `packages/app/perf/navigation.bench.ts` (the latter selects `[data-action="composer-model"]`). Benchmark any composer change against `origin/dev` with strobe before shipping.

**Constraints**: no new persistence schema, no generic queue/transaction layer, no new parallel truth (FR-026/FR-035); every existing test assertion stays in force (FR-028 and the constitution's validation gate); phone widths must open both pickers as drawers; the two variant controls must have distinct accessible names.

**Scale/Scope**: ~10 files in `packages/app`, 1 file in `packages/core`; no new production module except one pure derived selector if needed (see Change map). No public API, protocol, or SDK change.

## Change map (exact functions)

1. **`packages/app/src/composer/editor/editor.tsx`** — control row (`:484-512`): render, inside `props.modelControlsVisible`, in order primary model chip (`props.modelControl`) → `view.variant` → `view.fallbackModel` → `view.fallbackVariant`. Add the fallback variant `<ComposerEditorConfiguredSelect mobileDrawer title={i18n.t("ui.promptInput.chooseFallbackVariant")} …>` beside the existing variant control, keeping `composer-variant-default` on whichever variant control currently shows `default`. Reuse `ComposerEditorConfiguredSelect`/`ComposerEditorSelect` unchanged.
2. **`packages/app/src/composer/composer.tsx`** — `ComposerModelControl`: drop the swap/clear `Button` block and the `swap` prop; keep the primary chip (`ModelSelectorDrawer`/`Button`, `data-action="composer-model"`, `data-action="composer-fallback-model"`) and pass the fallback picker its opposite-slot key. Fallback chip content switches to a three-state selector (model name / "None" / "Same model") driven by `fallbackStatus`.
3. **`packages/app/src/composer/model.ts`** — `createComposerModel`: `view.fallbackModel` (chip label + picker trigger data) and `view.fallbackVariant` built from `adapter.controls().model.fallback.variant.{list,current,set}` — the existing fallback variant view (`selection.tsx:808-843`), which writes the config `fallback.variant` field. No new variant store. `variants()`/`view.variant` stay as they are except that the recorded-variant rule (item 8) changes what `current()` reports after a model change, and both variant controls read their options through `fallback.variant.list()`/`selection.variant.list()` so a model with a single variant shows no control for it.
4. **`packages/app/src/composer/selection.ts` — wrapped slot objects (the coordination boundary).** `createComposerControls` builds `primarySlot` and `fallbackSlot`: structural copies of `input.model ?? local.model` and `createFallbackModelSelection()` that override only `set`, `variant.set` and `variant.current`, keeping every other member (`trackSessionCommit`, `preview`, `cycle`, `favorite`, `list`, `current`, `key`, `recent`, `ready`, `visible`, `setVisibility`) so `composer/submit.ts:357/:411/:555` and `providers/models/unpaid.tsx:55` keep working. Every write from a picker, a command, the connect dialog or a variant select goes through these objects, which is what makes the exchange, the pair-variant rule and the visibility rule unconditional inside the composer. The wrapped `variant.current(item)` also answers for the opposite-slot model with the variant that model carries in the pair, so the picker's flyout check mark (`select-dialog.tsx:1040/:1177`) matches what an exchange will produce rather than the per-model preference the model would get if selected fresh. Bounded deliberately: it returns `pairVariant` **only** when the `item` argument names the model currently held in the other slot; for its own model, and for the no-argument form `composer/model.ts` uses to render the chip, it delegates to the underlying owner unchanged. Without that bound, an `inactive` fallback would change what the primary chip displays and would contradict `e2e/regression/mobile-model-pickers.spec.ts:141`, which asserts the flyout's current-variant check mark for the slot's own model.
5. **`packages/app/src/session/composer/selection.ts` — exchange phase beside the pair rule.** `swapModelPair` and `ComposerModelPair` stay as they are. Added next to them: a pure phase for one user action — `idle | exchanging({ attempt, restore, applied, half })` with a terminal `unresolved` — and `transitionPairExchange(state, event)` over a closed event union (`exchange.claimed`, `pair.written`, `record.failed(side)`, `slot.changed`, `target.changed`, `disposed`) returning `{ state, effects }`, where the effects name the owners' own writes. `composer/selection.ts` is the thin driver: refuse before claiming (the same rules the owners guard on — `validModel`/`valid()` at `selection.tsx:616` and `composer/selection.ts:263` for the primary target, `models.find` at `:865` for the fallback target), call `swapModelPair` for the pair and its carried variants, issue the writes inside one `batch` with a re-entrancy guard so its own writes do not supersede the exchange it is performing, and re-dispatch machine events when an owner reports an outcome. No queue, no lock, no shared transaction: each owner keeps owning its own ordering and rollback.

## Exchange state-transition design

Both slots keep their own machine. The coordinator adds one non-durable phase: the pair it must put back if an outcome says the action did not land, plus an attempt token so an old outcome cannot act on a newer world.

### Signals available from the existing owners

| Outcome | Signal in the existing code | Observed when | Effect on display today |
|---|---|---|---|
| Fallback half rejected | `fallbackUpdateState.save(value, failed)` rejection (`fallback-update.ts:44-50`) | after that write's `updateConfig` → `PATCH /api/experimental/config` rejects | `publish(undefined)` drops the optimistic override, so the chip shows the last recorded config value, and the toast fires |
| Primary record write rejected | `persistStore` dispatching `write.failed` with `{ attempted, fallback }` (`persist.ts:86`, `:93` for a `setItem` that returns `false`, `:96-99` for a rejection), machine moving `last` back to `fallback` and staying dirty (`persist-machine.ts:108-112`) | one save window after the edit — `persistSaveDelay = 100` (`persist.ts:13`) — not synchronously | **none**: the store keeps the user's value and retries on the next flush; the only visible signal today is the app-wide storage notice (`storage.ts:168` → `storage-machine.ts:38`) |
| Primary commit unacknowledged | `commit.timed-out` / `commit.cancelled` in `selection-machine.ts` (`COMMIT_ACK_TIMEOUT_MS = 10_000`) | 10 s after the submit path's `trackSessionCommit` (`composer/submit.ts:357/:411/:555`) | keeps showing the local selection — **not a failure** under the corrected FR-017, and never a compensation trigger |
| Server echoes a different durable value | `commit.reconciled` → `committed` phase | when the echo lands | the machine shows the server's value — also never a compensation trigger |

The two failure directions are asymmetric in kind, and the plan must respect that: the config half reports per write to whoever asked; the record half reports per save window to nobody outside the persistence layer. The primary half has no synchronous failure — its only synchronous "cannot record" cases are the validity guards (`validModel` at `selection.tsx:616`, `valid()` at `composer/selection.ts:263`, `models.find` at `:865`), which the refusal check covers up front (FR-020).

### Ordering (one sequence for all four directions)

1. Check **both** targets before anything is claimed: the model moving into the primary slot must satisfy the primary owner's own guard (catalog + connected for this workspace), and the model moving into the fallback slot must satisfy the fallback owner's `models.find` guard. Anything failing → no write at all, `exchange` returns `false` (FR-020).
2. Capture `restore` — model + variant of each slot — and whether each target model is currently visible (`models.visible`), so a flip can be undone.
3. Write **the slot the user acted in first**: its model, then its variant. Model-then-variant per slot is not stylistic — `variant.set` resolves against `current()` (`selection.tsx:662`, `composer/selection.ts:318`), so a variant written before its model would land on the wrong slot.
4. Write the **displaced model into the other slot** with the variant `swapModelPair` carries (cleared to the model's default when the destination does not offer it, FR-010), then restore any visibility the writes flipped.
5. All of steps 3-4 inside one `batch` and one re-entrancy guard (the coordinator's own writes must not count as a newer action).
6. Report the applied pair to the phase (`pair.written`); outcomes arrive later as events.

This replaces the previous claim that the primary-picker direction writes the fallback first; the traces below match this order. `batch` buys one render and one save window — **nothing more**. It does not make the two durable writes atomic, and it does not couple their asynchronous failures; the "never shows the same model in both slots" invariant rests on the batch plus the inactive-fallback presentation, and the ordering rule is only about which slot takes effect first.

### Traces

1. **Success, primary picker (row click).** `ModelList` row → `controller.select(B)` (`select-dialog.tsx:202`) → wrapped `set(B)`: identity equals the fallback slot's model → phase claims attempt *n* → refusal checks pass → `batch`: `selection.set(B)` then `selection.variant.set(Bv)` (variant carried from the fallback slot), then `fallback.set(A, { variant: Av })`, then visibility restore. One render; chips read B / A. `PATCH` and the eventual session commit are still in flight (FR-019: not one durable operation).
2. **Success, primary picker (flyout or keyboard Enter).** `activateMenu` (`:703-706`) or Enter on the pre-highlighted option (`:928-930`, pre-highlight comes from `:964` using `controller.variant(item)`) → `select(B, v)` → the exchange above, and **then** the picker's `model.variant.set(v)` (`:516`) lands last, so the variant the user clicked wins over the carried one — correct, because that click *is* an explicit variant intent. Consistency requirement: the flyout's check mark is computed with `controller.variant(item)` = the wrapped `variant.current(item)`, which for the opposite-slot model returns `pairVariant` — the same value the exchange writes — so the menu can no longer preview "Default" and then produce "xhigh". A row click passes `variant === undefined` and writes no variant, so a carried variant is never destroyed by a row click.
3. **Success, fallback picker.** Clicked slot is the fallback: `fallback.set(A, { variant: Av })` first, then `selection.set(B)` + `selection.variant.set(Bv)`. Empty or inactive fallback slot → no-op (FR-006 + Assumptions).
4. **Upfront refusal (FR-020/FR-010).** Either target fails its owner's guard → the phase never leaves `idle`, both slots' models and variants untouched, `exchange` returns `false`; the picker's affordance stays as today (`dialog.model.unavailable` labels the chip, not the pair).
5. **Fallback-half failure (FR-032, direction 1).** The `PATCH` rejects → the owner already reverted its own display and calls `failed` → the coordinator dispatches `record.failed("fallback", attempt)` → with the exchange still pending, compensation re-writes the primary from `restore` (`selection.set(restore.primary)` + `variant.set`) inside one `batch`; the fallback half needs no re-write because it reverted itself. Toast reports (existing path). Honest caveat: "reverted itself" means back to its **last recorded** config value, which equals `restore.fallback` only if that half's earlier write did land — if it did not, the two slots legitimately hold what their records hold, the phase goes `unresolved`, and the `inactive` presentation keeps the display collision-free. Loop prevention is **not** a ban on writing the failed half: here the fallback half needs no re-write because the owner already dropped its own optimistic override, whereas Trace 6's record failure *does* re-write the failed primary half from `restore`. What is forbidden is recursion — a compensation write must never itself trigger another compensation: the phase releases the attempt as it compensates, so a `record.failed` arriving for an attempt it no longer holds returns the same state with no effects, and at most one report is issued.
6. **Primary-half failure (FR-032 direction 2, qualified by FR-018).** ~100 ms later the save attempt fails → `recordFailure()` reports an observation whose `attempted` payload carries the pair this exchange wrote for this composer's session key, with no successful save of that document landed since the exchange's write, and whose attempt the phase still holds → the coordinator dispatches `record.failed("primary", attempt)` → compensation writes **both** halves back from `restore`: `selection.set(restore.primary)` + `variant.set(restore.primaryVariant)` and `fallback.set(restore.fallback, { variant: restore.fallbackVariant })` through the fallback owner (so it queues on its own `pending` chain and cannot interleave with another config write). The fallback's second write is an explicit re-write, not a reliance on `publish(undefined)`: after a *successful* half the optimistic override is already cleared, so the last recorded value would be the new one. An observation whose payload predates the pair, one already cleared by a later successful save of the same document, or one whose attempt the phase no longer holds produces no compensation at all. The honest reading is "the exchange's values are not known to be durable", not "this exchange's write failed": `persist.ts:75-101` coalesces every edit to that document into one save window, so no per-action write exists, and the captured id is a sequencing token only.
7. **Compensation failure — not assumed to succeed.** If the compensating writes fail (the realistic case: a quota failure is workspace-wide, and a rejected `PATCH` usually still stands), the phase moves to `unresolved`, the failure is reported once through the existing toast paths, nothing is re-attempted by the coordinator (each owner already owns its own retry: the persist layer stays dirty and retries on the next flush; `fallbackUpdateState` stays serialized), and the displayed pair is whatever the compensation attempted — never a pair that *shows* the same model twice, because the inactive-fallback presentation suppresses that display regardless. The plan claims restoration of the displayed pair and of the write attempts, never that both durable records hold it; `spec.md`'s new Assumptions bullet states that limit, and FR-019/Out-of-Scope already forbid durable atomicity and better storage.
8. **Stale compensation (the required sequence: initial A/B → exchange to B/A → user selects primary C → old exchange fails ⇒ final C/B).** Attempt *n* pending with `restore = A/B`. The user's next action — any write to either slot, including a variant-only write or an agent-cycle write — passes through a wrapped setter, dispatches `slot.changed`, and the phase discards the pending exchange. When the old `PATCH` then rejects, its `failed` callback carries attempt *n*; the transition returns the same state (no pending exchange with that attempt), so no compensation runs. **Final state is the pair C/B**: the primary slot keeps C, because the user's newer selection is never compensated over, and the fallback slot shows **B** — the rejected write's optimistic override is dropped by the owner itself (`publish(undefined)` at `fallback-update.ts:44-50`), which restores that slot's own authoritative confirmed state, its last recorded fallback. **Never C/A**: A was never recorded, so it cannot survive its own rejection; the failed old exchange has no authority to compensate over the newer primary. **Never A/B**: the discarded attempt's `restore` cannot re-write C. Invariant: the newer user primary survives, a failed old exchange cannot compensate over it, and the fallback reflects its own confirmed state. Per-owner suppression cannot do this: `fallbackUpdateState`'s revision check and `selection-machine.ts`'s attempt ids only stop each owner's own stale write, so cross-owner suppression lives in the coordinator's attempt check (FR-018).
9. **Rapid exchanges.** One attempt token per composer; only the newest pending exchange may compensate. An older exchange's write is still *sent* (its `save` already queued on `pending`) and its publish is dropped by `revision !== state.revision` (`fallback-update.ts:44-47`) — the coordinator must not claim otherwise; the visible pair follows the newest action (FR-015).
10. **Identity change.** A route/session change, `session.deleted`, composer unmount (`disposed`) or a different server dispatches `target.changed`, which discards the pending exchange without compensating — the previous target's pair must not be written into a new target. `createFallbackModelSelection()` instances share one `fallbackUpdateState` per `server.ctx.sync` (`fallback-update.ts:13-28`, WeakMap), so the chain survives a composer change and not a server change; `createComposerControls`' phase dies with the composer.
11. **Variant-only and agent-cycle actions never exchange** (FR-002 independence), but they still mark `slot.changed` for staleness purposes. `createComposerModelSelection`'s agent-cycle writes (`composer/selection.ts:177-183`) flow through the wrapped draft setter, so a pending draft exchange is superseded by an agent switch rather than compensated into it.

### Required extensions (with the evidence that justifies each)

The spec's FR-032 guarantee — restore the complete pre-exchange pair when **either** half cannot be recorded — is implementable through the existing owners, but not with today's visible APIs alone. Two focused extensions are required; a third item is an honesty limit rather than code.

| Extension | Exact existing API touched | Minimum change | Why nothing simpler works |

## Risks (each tied to a reachable path)

1. **Strict accessible-name locators break.** `component-tests/composer.spec.ts` and `mobile-model-pickers.spec.ts` use `getByRole("button", { name: "Choose model variant", exact: true })`. A second same-named control makes those strict lookups fail — hence the new key. RTL: labels are direction-neutral, but the drawer order assertions in the mobile spec iterate both directions and must be re-read for the added control.
2. **`composer-variant-default` opacity.** `editor.css:78` hides `.composer-variant-default` when the composer is not hovered/focused. Applying the class to both variant controls independently is required (FR-003); applying it to only one leaves the other permanently visible and breaks the "reveal under the same conditions" contract.
3. **Loading/preview choreography.** The fallback chip is gated by `<Show when={!props.loading}>` and the primary chip by `modelControlsVisible`; moving the fallback chip into the editor row must preserve both gates and the model-chip machine's pending/cancelled path, or a late catalog can pop a picker the user has moved on from (the e2e case at `composer.spec.ts:580` guards this).
4. **Hidden models, visibility, and the `recent` list.** `{ recent: true }` only pushes onto the recent list (`models.tsx:push`, capped by `RECENT_LIMIT = 5`) — it does **not** change visibility. The flip comes from the unconditional `models.setVisibility(item, true)` in all three write sites: `selection.tsx:630` (session), `:881` (fallback), `composer/selection.ts:272` (draft), so today's `swap()` already re-shows a model the user hid. Decision for this feature: an exchange must **preserve** the user's hidden state — the coordinator captures `models.visible(target)` for both targets and re-applies `setVisibility(item, false)` inside the same batch (existing APIs only, one store update per key); it passes `recent` only for the model the user clicked. Checked evidence for that rule: no test asserts that selecting a model changes visibility — the only visibility assertions in the app's tests are persistence-schema round-trips (`runtime/server/persistence.test.ts:99/:109`) and no-op `setVisibility() {}` stubs in mock slots (`composer/submit.test.ts:36`, `test-browser/composer-submit-loading.test.ts:22`). Those mocks also confirm the wrapper's member list: they already supply `visible`, `setVisibility`, `recent`, `favorite` and `list`, and an optional `recordFailure` costs them nothing. `include` keeps the hidden model offered in the opposite picker regardless (FR-024/FR-033). This is a deliberate change from today's swap behaviour and is now **specified** behavior: FR-033 states that an exchange leaves a model's visibility as the user set it, with its own acceptance scenario (User Story 2 scenario 11), and names it an explicit exception to the existing selection-side re-show rule, which keeps its current behavior outside the composer's exchange. Deleting the capture/restore is therefore a spec violation, not a reviewer option; the constitution's Principle I is satisfied because the specification covers the change rather than leaving it silent.
5. **Draft vs session selection are two owners with two variant rules.** FR-034's fix has two sites: the session owner's `set()` (`selection.tsx:626`, with the session-only repair at `:629`) and the draft owner's `set()` (`composer/selection.ts:266`, which writes `variant: undefined` on any model change). Both must seed through one shared selector (`recordedVariant` in `providers/models/variant.ts`), or a draft and a session will disagree; `variant.current()` already prefers the per-model store (`preferred:` at `:652`), so a recorded/displayed mismatch is the failure mode. The fixture case at `:396` pins the session half; its draft-mode twin is the new regression. Related: the two owners refuse differently (`validModel` at `selection.tsx:616` vs `valid()` at `composer/selection.ts:263`), so the exchange's refusal check must ask the *slot* being written, never a hard-coded rule.
6. **Core `modelKey` widening.** Attempt-tracking now collapses variants of one model, so a future intent that stages two variants of the same model as distinct recoveries would stop working. FR-031 asks for exactly this; the added core scenario makes the intent explicit so the collapse is deliberate, not incidental.
7. **Mock-server config writes.** `test-browser/fixtures/model-selection.ts:59` mocks `updateConfig`, but the e2e mock answers `PATCH /api/experimental/config` with a static `noContent` (`mock-server.ts:945`) and serves `configEntries` only through `GET /api/config`. Reload scenarios (FR-012/013/021) need the mock to apply the PATCH to the config it later serves; if that state is not added, the explicit-off reload keeper would silently pass on a stale value. This is a required harness change, not an optional convenience.
8. **Rule duplication with the core.** The identity rule and the legacy-fallback default exist on both sides of the app/core boundary (the existing comment at `selection.tsx:743` records that `ConfigFallback.LEGACY_MODEL_FALLBACK` cannot be imported by the browser). FR-035's "one meaning" is enforced by paired tests on both sides, which is weaker than a shared module; flagged for review, and any future import fix is out of scope.
9. **The wrapped slot object is a structural copy.** `composer/submit.ts:357/:411/:555` calls `controls().model.selection.trackSessionCommit`, and the pickers read `list`, `visible`, `favorite`, `recent`, `ready` and the optional `preview`. A copy that drops any member silently breaks submission or the catalog display; `composer/submit.test.ts:795/:842` is the existing guard for the commit path, and `typecheck` catches the shape only if the wrapper is typed as `ModelSelection` rather than inferred.
10. **Record failure is asynchronous and flush-driven.** The save happens on a `persistSaveDelay = 100` window (`persist.ts:13`) and also on `visibilitychange`/`pagehide` (`persist.ts:26-31`), so `record.failed` can arrive ~100 ms later or while the page hides. The phase must tolerate an outcome with no pending exchange (drop it), and tests must drive it with `flushPersisted()`/`setSystemTime` rather than a sleep.
11. **`recordFailure()` is per workspace document, not per action.** `Persist.serverWorkspace(scope, directory, "model-selection")` (`selection.tsx:176`) holds every session's selection in one record, and `persist.ts:75-101` coalesces every edit to that document into **one** save window, so there is no per-action write to attribute a failure to. What the observation can honestly establish is that the exchange's values are not known to have landed — via the failed write's `attempted` payload carrying the pair, no successful save since the write, and the phase still holding the attempt. The compensation is therefore one attempt, one report, and directional; the plan must not claim it identified which write failed, and any demand for action-level causation is a blocking gate that would require a persistence-layer write identity (out of FR-026's scope).
12. **`fallbackUpdateState` is shared per server.** The WeakMap in `fallback-update.ts:13-28` means the first composer created for a `server.ctx.sync` owns the `write` closure; per-call `failed` callbacks are safe, but any future per-composer write behaviour would be silently ignored.
13. **Flyout preview versus the carried variant.** `pairVariant` must be the single source read by both the wrapped `variant.current(item)` (used by `select-dialog.tsx:1040` and the flyout's `aria-checked` at `:1177`, and pre-highlighting at `:964`) and the exchange's variant writes. If they are computed separately, the menu can preview Default and produce `xhigh`, and the keyboard `Enter` path (`:928-930`) would then write Default over the carried variant.

## Spec correction

Applied to `spec.md` **before** finalizing the plan (Principle III + IX + the complexity gate):

> **FR-017**: If a one-slot primary model change's own record reports a failure, the system MUST revert only the primary slot to its last recorded value and MUST leave the fallback model and variant unchanged. A primary change whose server confirmation does not arrive inside the existing confirmation window is not a failure: the primary slot keeps showing the user's choice, as it does today, and reconciles when the server's value arrives.

Reason: the primary owner tracks server acknowledgement separately (`selection-machine.ts`: `awaiting-ack` → `commit.timed-out`/`commit.cancelled` keep the local override; `COMMIT_ACK_TIMEOUT_MS = 10_000`), and `selection-machine.test.ts:141` ("a commit the server never echoes stops waiting after the timeout and keeps the selection") plus `:177` (cancelled keeps `choice b`) assert exactly that. FR-017's wording also appeared in acceptance scenarios 5 and 10, which were narrowed the same way. Implementing the literal wording was rejected: it needs a second revert path around `selection-machine.ts`, deletes existing assertions (validation gate), and creates two claims about the same commit's outcome. FR-016 and FR-032's *requirements* are unaffected, and the five settled clarifications are unchanged. One Assumptions bullet was added (no FR wording changed) to state what FR-032 does **not** promise when the restore itself fails — the composer guarantees a valid displayed pair and no late restore over a newer choice, not that both durable records hold the pre-exchange values after two failed writes — because the primary's storage failure signal is workspace-wide (`Persist.serverWorkspace(scope, directory, "model-selection")`, `selection.tsx:176`) and a failed save usually sinks the compensating write too. A plan that claimed otherwise would be asserting durable atomicity, which FR-019 and Out of Scope forbid.
