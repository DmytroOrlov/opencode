## Decisions

1. **Exchange lives on the composer's wrapped slot objects, not in the owners.** `createComposerControls` is the only existing boundary holding both owners (session `input.model ?? local.model`, and `createFallbackModelSelection()`). Wrapping = a structural copy overriding only `set`, `variant.set`, `variant.current`; every other `ModelSelection` member must survive, because `composer/submit.ts:357/:411/:555` calls `trackSessionCommit` and the pickers read `list`/`visible`/`favorite`/`recent`/`preview`. Two call sites must be fixed for that claim to be true: `session/composer/region.tsx:311` calls `useComposerCommands()` with no argument, so `commands.tsx:31` resolves `model = local.model` and `/model`, `shift+mod+d`, the connect dialog (`commands.tsx:42`) and the usage dialog's "switch model" bypass the pair; `new-session/screen.tsx:55` already passes an object and must pass the wrapped one. The fallback-inactive presentation (FR-029/030, required anyway) is the invariant covering the writers that stay outside: `runtime/plugin/mounted-session.ts:258-268` (plugin `setModel`), `session/usage-exceeded-dialogs.tsx:122`, `providers/models/manage.tsx` (visibility only). V1's `enqueue`/`persist` queue is not carried over: both owners already serialize (`fallbackUpdateState.pending`, machine attempt ids), so a composer-level queue would be parallel truth (FR-026).
2. **`swap()` → an exchange with pre-flight refusal for both targets.** FR-020 demands refusal *before* either slot changes; today's `swap()` (`composer/selection.ts:106-131`) writes the primary after `swapModelPair` succeeds, and the owners' guards return silently (`validModel` at `selection.tsx:616`, `valid()` at `composer/selection.ts:263`, `models.find` at `:865`). Because the two primary owners refuse with *different* predicates, the check must ask the slot being written, not a shared rule.
3. **Compensation in both directions, and it is not a transaction.** The two halves fail differently: the config half reports per write to whoever asked (`fallbackUpdateState.save(value, failed)`, `fallback-update.ts:34-51`), while the record half reports per save window to nobody outside the persistence layer — `persist.write` → `setSaved` (`selection.tsx:214`) → dirty store → `schedule-save` on a `persistSaveDelay = 100` window (`persist.ts:13`, also flushed on `visibilitychange`/`pagehide`, `persist.ts:26-31`) → `setItem` returning `false` or rejecting dispatches `write.failed` (`persist.ts:86/:93/:96-99`), and the machine moves its `last` pointer back to the stored fallback while keeping the store dirty and retrying (`persist-machine.ts:108-112`). So FR-032 needs: for a rejected config write, restore the primary; for a failed record write, restore **both** halves explicitly (after a half *succeeded*, the optimistic override is already cleared, so "the last recorded value" is the new pair, not the old one). Compensation is not assumed to succeed — a quota failure is workspace-wide, so it usually fails too — and then the phase ends `unresolved` with one report, no loop, and the display kept valid by the inactive-fallback state. The claim stays "displayed pair + write attempts", never "both durable records hold the pair". The record half's signal is read as an **admissible observation** (the machine's `write.failed` payload plus a monotonic id from the driver that only sequences observations), never a boolean: it is scoped to the whole workspace document and `persist.ts:75-101` coalesces every edit to it into one save window, so an observation counts for the claiming exchange only when its `attempted` payload carries the pair that exchange wrote for this session, no successful save of that document has landed since the write, and the phase still holds the attempt — otherwise a prior-window failure or a write to another document compensates a pair it does not own. What that licenses is "the exchange's values are not known to be durable", never "this exchange's edit failed". For the stale sequence the phase's attempt token is what settles it: initial A/B → exchange to B/A → user selects primary C → the old config write then fails leaves **C/B** (the newer primary survives and the fallback returns to its own last recorded value), never C/A and never A/B.
4. **Both writes in one `batch`, and `batch` is not the safety mechanism.** Solid defers observers to the end of the synchronous block, so a `batch` gives one render and one save window, which is what FR-019's "no point where the same model shows in both" needs. It provides neither durable atomicity nor coordination of the async failures: that is the exchange phase's attempt token, and the invariant is reinforced by the inactive-fallback presentation. Per-slot ordering inside the batch is load-bearing: `variant.set` resolves its target from `current()` (`selection.tsx:662`, `composer/selection.ts:318`), so each model write must precede its own variant write.
5. **Variant controls stay two controls, distinguished by name.** `component-tests/composer.spec.ts` selects the variant control by the accessible name "Choose model variant" (`ui.promptInput.chooseVariant` in `packages/ui/src/i18n/en.ts`). Constitution forbids changing existing English copy, so the fallback variant control gets a new key (`ui.promptInput.chooseFallbackVariant`) rather than a disambiguating refactor. Both controls get the `composer-variant-default` quiet-at-rest class (`editor.css:78`).
6. **Fallback variant writes the config field, not a store.** `FallbackSelection.variant.set` (`selection.tsx:825`) already rewrites the config `fallback` record with the new variant; FR-018 is satisfied by reusing it and nothing new is persisted.
7. **FR-034 has two sites, not one.** The session owner's `set()` (`selection.tsx:626`) seeds `INHERIT_VARIANT` when the model changes and re-reads the per-model variant store only for real sessions (`:629`, guarded by `id()`); the draft owner's `set()` (`composer/selection.ts:266`) is harsher still — it writes `variant: undefined` whenever the model changes (`same ? (selection.variant.current() ?? null) : undefined`). Both must seed the value already recorded for the newly selected model (`models.variant.get` → `durableVariantSelection`) through one shared selector, or a draft and a session disagree. `variant.current()` already prefers the per-model store (`preferred:` at `:652`), so a recorded/displayed mismatch is the failure mode; the fixture case at `:396` pins the session half and its draft-mode twin is the new regression.
8. **The picker offers the opposite slot's model as a normal row, and the row's visibility side effect must be undone.** `allModels()` (`:481`) filters `model.visible(...)`; adding an `include` key restores the row without forking the picker's search/flyout/drawer/keyboard behaviour, and the write guards (`validModel`/`valid()`/`models.find`) ignore visibility, so hidden models stay selectable (FR-033). Checked: `{ recent: true }` does **not** change visibility — it only pushes onto the recent list (`models.tsx` `push`, `RECENT_LIMIT = 5`). The flip comes from the unconditional `models.setVisibility(item, true)` in all three write sites (`selection.tsx:630`, `:881`, `composer/selection.ts:272`), so today's `swap()` re-shows a model the user hid. The spec asks only that the model be *selectable*, never that a hidden model become visible, so the plan preserves the preference: capture `models.visible(target)` for both targets and re-apply `setVisibility(item, false)` in the same batch, with `recent` passed only for the clicked model. No existing app test asserts a visibility flip on selection (`setVisibility` appears in no app test), so FR-028 is not at risk.
9. **A model-plus-variant pick is one intent, and the picker already expresses it that way.** `createModelSelectorController.select(item, variant)` (`select-dialog.tsx:513-518`) writes the model (`model.set(item, { recent: true })`) and then the variant **only when `variant !== undefined`** (`:516`). So a row click (`:202`, and `SearchList`'s `onSelect` at `:1123`) carries no variant and cannot destroy one, while the flyout (`activateMenu` `:703-706`) and keyboard `Enter` (`:928-930`) pass an explicit `options[index] ?? null` — that click *is* variant intent and must win over a carried variant. Ordering is load-bearing: `variant.set` resolves its target from `current()` (`selection.tsx:662`, `composer/selection.ts:318`), so each model write must precede its own variant write or the variant lands on the wrong slot. The one hazard is that the flyout's option list, its check mark (`:1040`, `aria-checked` at `:1177`) and its keyboard pre-highlight (`:964`, seeded from `options.indexOf(controller.variant(active.item))`) all ask `controller.variant(item)` = `model.variant.current({ providerID, modelID })` — the per-model preference, i.e. what the model *would* show if selected fresh, not what it carries in the pair. Hence the wrapped slot overrides `variant.current` with one `pairVariant` selector shared by preview and write: otherwise the menu previews "Default", `Enter` writes `undefined`, and the exchanged variant is lost.
10. **`new-session/composer-adapter.ts` shows the draft owner is reached the same way** — `:95-96` builds `createComposerModelSelection()` and hands it to `createComposerControls({ model })`, so wrapping inside `createComposerControls` covers drafts and sessions at once; `region.tsx:311` is the only call site that passes nothing.
11. **Recovery identity change is one line.** `modelKey` dropping `variant` makes `served.ref === currentModel` and `attemptedFallbacks` variant-agnostic. Checked: no existing core scenario stages two fallbacks differing only by variant (`session-runner.test.ts` fallback scenarios at `:6362`, `:6403`), so FR-028 holds.
12. **FR-017 corrected rather than implemented literally** (see plan.md "Spec correction"). The primary owner's ack-timeout behaviour is asserted at `selection-machine.test.ts:141` and `:177`, and an unacknowledged commit is deliberately *not* a failure. The primary's *record* failure is a different, real signal that lives one layer down (`write.failed` in `persist.ts:86` / `persist-machine.ts:108`) and is not currently returned to any caller — that is the gap FR-032's primary direction needs closed (see the "Required extensions" table in plan.md), and it closes by carrying the owner's own failure payload plus a driver-issued id, not a boolean: the record covers the whole workspace document and coalesces edits into one save window, so the phase must be able to tell an admissible observation — its `attempted` payload carries the pair this exchange wrote for this session, and no successful save of that document has landed since the write — from a prior-window failure, a different document, or one already superseded by a later successful save. The id sequences those; it never says which edit failed.

13. **Per-owner suppression cannot cover a cross-owner compensation.** `fallbackUpdateState`'s revision check (`fallback-update.ts:44-47`) suppresses only the fallback's own stale publish, and `selection-machine.ts`'s attempt ids only cancel the primary's own commit callbacks. A compensation is different in kind: it is issued *by the coordinator, in the other owner*, after an outcome arrives from the first. With no attempt token of its own, the sequence A/B → exchange to B/A → user selects C → old exchange's `PATCH` rejects would restore A/B and destroy C — a reachable wrong-state, not a theoretical one. So the exchange phase carries one attempt token per composer and discards a pending exchange on any newer write to either slot (`slot.changed`), on an identity change (`target.changed`: route/session change, `session.deleted`, composer unmount, server change), and on `disposed`. With the token, that sequence settles as **C/B**: the newer primary C survives, and the fallback half reverts to its own last recorded value because the owner drops the failed optimistic override (`fallback-update.ts:44-50`) — never C/A, since the rejected value was never recorded. `createFallbackModelSelection()` instances share one `fallbackUpdateState` per `server.ctx.sync` (`fallback-update.ts:13-28`, WeakMap), so the config chain survives a composer change; the phase does not, which is the correct asymmetry.
