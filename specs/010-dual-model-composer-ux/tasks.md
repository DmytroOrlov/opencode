**Organisation**: Tasks are grouped by **architectural ownership** inside each user-story phase, so the failure-safe pair coordinator and variant-selection integration land before final UI validation. Each task is a coherent unit, not a microstep.

## Format: `[ID] [P?] [Story?] Description with file path`

- **[P]**: safe to run in parallel with the other tasks **in the same phase or slice** — no file in common with them, and no dependency on the *output* of an unfinished task. It does not mean "green now": a test task marked `[P]` may legitimately stay red until the implementation task in its slice lands (that is the test-first contract, not a violation). Tasks sharing a file — `packages/app/src/composer/selection.ts`, `packages/app/src/session/composer/selection.test.ts`, `packages/app/src/providers/models/select-dialog.tsx`, `packages/app/src/providers/models/selection.tsx` — are never `[P]` against each other and run serially inside the slice.
- **[Story]**: `US1`…`US5` map to `spec.md` → User Scenarios (US1 four-control pair at a glance, P1 · US2 automatic exchange, P1 · US3 None + off/inactive, P1 · US4 scoped/visible/durable, P2 · US5 keyboard/phone/compact, P2)
- Setup, Foundational and Polish tasks carry **no** story label
- Every task names exact files, the existing APIs it reuses, its invariant, its tests, and its acceptance evidence; dependencies appear in parentheses at the end of the description
