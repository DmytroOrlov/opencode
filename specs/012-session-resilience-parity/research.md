## R1 — Identify the writable directory, then borrow its coordination

**Decision — effective filesystem authority.** The resource key MUST be derived from the effective Config filesystem authority used for actual `Config.update()` operations, not from an independently resolved platform filesystem that might differ under SDK graph replacements. Resource identity is the pair `(proven backing-filesystem namespace, writable-directory identity)`. Two independently acquired wrappers over the SAME backing directory MUST obtain the same key. Two different backing filesystems MUST NOT share a coordination pair merely because they expose identical directory strings or device/inode values. The directory identity is established before its config leaf files exist and does not change when atomic rename replaces a config document. An unknown or unverifiable backing namespace MUST fail embedded-host acquisition rather than silently merge, split or guess a resource key. Host-local ownership and cross-process exclusions remain unchanged.

**Namespace producer and forwarding.** Add an optional enumerable symbol-keyed provenance capability on the effective Effect `FileSystem.FileSystem` value, with its typed accessor exposed through `FSUtil`. The default provider in `packages/util/src/effect/app-node-platform.ts` attaches an opaque module-owned token when it constructs the trusted local `NodeFileSystem.layer` binding. Independent layer acquisitions in the same runtime filesystem realm receive the same token. The platform profile may supply that token only for a backing filesystem it owns. `FSUtil.layer` already builds from the injected filesystem and spreads its methods. Preserve that delegation and forward the capability through the spread. A recorder such as `packages/server/test/fixture/config-fs.ts` should acquire the annotated local platform layer and forward the capability from its delegate. A direct `FSUtil.node` replacement must likewise retain or supply provenance for its own operations. A virtual or delegated provider supplies an opaque token allocated once by the backing store owner and reuses it for that store's lifetime across wrappers and acquisitions. If a wrapper routes paths across stores, its provenance lookup must identify the actual backing store for the writable directory and its config children, or decline that directory. Only a transparent wrapper may forward the delegate's token unchanged. Tokens are compared by identity and are independent of wrapper identity, printed paths and inode numbers.

**Directory probe.** Resolve the effective Global config path with existing Config path-join normalization. With proven namespace capability, create a missing directory via the acquired `FSUtil.Service.ensureDir`, then use that same service's strict `realPath` and directory `stat`. Use a reliable directory device/inode pair inside the proven namespace, or an alias-stable canonical directory path guaranteed by that backend where inode is unavailable. Missing provenance, ambiguous namespace, failed probes or unreliable identity fail acquisition before a pair is registered. For the standard embedded Global binding, move creation of just the writable config root to this effective-FS initialization. `Global.layerWith` currently makes it with direct OS I/O, so retain its existing setup for other roots and its ordinary standalone behavior. A virtual Config root is initialized by its filesystem provider.

**Rationale** `makeRoutes` applies options and then runtime overrides. Its standard binding uses `Global.layerWith`, whose defaults differ from the ambient `Global.node` environment handling. Config discovers `Global.Service.config` and falls back to that same directory in the update path even with global discovery disabled. `config.file` and inline content have separate read semantics. The pinned Effect `FileSystem.Info` exposes `dev` and optional `ino`, and `realPath` resolves path aliases. `FSUtil.resolve` intentionally falls back on access denied or missing paths and preserves some Windows spelling, so its return value alone cannot establish identity. `ServerWorkerd.replacements` changes the database and Core execution filesystem service, while Config still uses the platform Global and utility filesystem selected by the bundle. Durable Object storage identity is irrelevant to Config. The current simulation replacements in `packages/simulation/src/backend/index.ts` replace the HTTP client. They leave the Config filesystem unchanged, so no simulation-specific token is required. A profile that replaces the effective Config filesystem must establish its own provenance or explicitly forward its delegate’s.

**Alternatives considered**

- Raw options, absolute spelling alone, a lowercased string, or lexical fallback on an identity error would respectively miss effective overrides, aliases, distinct case-sensitive directories, or uncertainty.
- File inode, symlink target file, hard-linked documents and byte identity would alias two rename slots or change identity on successful replacement. Two distinct config directories remain distinct even when their documents are linked or identical. Config's file-entry selection and rename semantics remain as implemented.
- A process-wide pair would couple independent resources. Independent pairs per build miss the demonstrated shared-directory case. Cross-process locking and live retargeting of a configured directory are outside this contract.

## R2 — Extend the binding and lifetime, preserving Config ownership

**Decision** A module-owned map at the Core application-graph boundary borrows one admission and intent pair per writable resource for embedded hosts. Acquire and increment, or create and register, in one synchronous critical section after identity is known. Scope each reference to the outer embedded graph. After standard, SDK/runtime and simulation replacements are finalized, the embedded route layer uses `LayerNode.group` and `LayerNode.compile` to acquire `Global.node` and `FSUtil.node` together with those same replacements in an outer scope. Compute the key from the captured `FSUtil.Service` and effective Global target. Before building routes, bind that exact FSUtil value and the captured Global value with the resolved Config directory into the final replacement list. Root, Location and SDK private instance Config then all use the same writer authority that produced the key. Keep the prerequisite scope alive through child graph disposal. Supply the pair through the existing replacement path to the root, ordinary Location map and SDK private selector. Release the reference after that host's requests, execution fibers and child graph scopes have closed. Only the last release evicts the entry. Surface missing provenance or identity as a typed startup `Error` through the existing embedded creation channel. The failed acquisition closes the prerequisite scope. If startup fails after the pair was acquired, its registered release runs when `EmbeddedHost.create` disposes the failed ManagedRuntime; it removes only the failed host’s reference. Generic standalone `AppNodeBuilder.build` keeps its default local pair and current explicit replacement behavior.

**Rationale** `AppNodeBuilder.build` already injects the two in-memory services as values. `SdkInstances.node` closes over the route replacement list and builds an additional `Instance.layer`; populating only the ordinary location map would leave this selector on a private pair. `OpenCode.create` owns `EmbeddedHost.close` via acquire/release, `OwnedFetch.close` aborts and drains requests before disposing runtime, and the existing location scopes own their children. A scoped reference shares exactly the two services and leaves Config caches, reload locks, transport, Bus, database, plugins and location lifecycle with their existing owners. Config's shared committed revision already lets a lagging reader reconcile against disk without taking admission recursively during recovery.

**Alternatives considered** A shared runtime or Config instance would share host data and publication. An unbounded map would retain abandoned revisions. Using each host's layer memoization alone cannot bridge distinct ManagedRuntime scopes. OS-file locks would add persistence and would still need a separate intent authority.

## R3 — Preserve entry order and protect ownership handoffs

**Decision** Reuse the 011 admission queue and intent revision line at resource scope. Reservation order governs commits. The highest accepted revision governs staging, with the revision itself retained when the override clears. A superseded in-flight intent does not reappear when a newer accepted intent retires. A committed predecessor becomes visible through Config's durable read, including when a newer intent fails. Explicit null disables fallback and omission only participates in durable order. Ensure reservation cleanup is installed before interruption can escape ownership transfer. Clear by the reserved revision on exit, including the interruption edge immediately after staging. Keep lease waits interruptible and install release as part of their granted-lease handoff, checking the generation and writer paths for a grant/interrupt boundary. Keep the existing masked forward-publication window from the temp-file transaction through rename, commit marker, reload and cleanup.

**Rationale** `Config.update` reserves before candidate validation, stages before predecessor and exclusive waits, then rereads and validates under the exclusive lease. `FallbackRuntimeIntent` holds a high-water mark and only clears its current revision. `Config.entries` already checks `committedRevision` independent of the staged line. `SessionRunCoordinator` holds shared admission until terminal settlement. Only these owners can safely release their participation. A sibling scope closing has no authority to clear the shared pair.

**Alternatives considered** Last-validation-wins breaks late B versus accepted C. Staging only under exclusive admission breaks visibility while A is running. Restoring an older pending override after a newer accepted override retires revives superseded intent. Broadcast or eager reload of every host would introduce another publication path.

## R4 — Separate safe failover from authorization to repeat a model

**Decision** Preserve the accepted retry and backoff path, including its ordinary fallback substitution after the wait. Add a distinct-only recovery disposition on a classified failure when the ordinary retry decision declines or is exhausted. It carries the failed attempt's original exit and whether durable history is safe to restart or continue. In this path use no retry event, schedule wait, or additional primary request. If no eligible target survives preparation, propagate the original terminal outcome. Reuse the failed physical attempt's existing settlement path and a fresh assistant for the next physical attempt. Preserve same-assistant behavior for the existing transparent retry path. Apply replay safety when dispatching either recovery path.

**Rationale** `SessionStep.attempt` owns provider and tool settlement. `SessionRunner.runStep` owns retry wait, context reload, compaction and model dispatch. Only the runner can resolve the latest intent against the effective agent, provider and variant. A production HTTP 401 flows through `RequestExecutor.statusError` and `provider-error.ts` as Authentication. With no header override, `AIError.isRetryable` declines it. `SessionRunnerRetry.policy` invokes the existing mutable hook when the schedule produces a decision, and returns immediately when that schedule is exhausted. Preserve a hook's in-budget ability to change the ordinary retry decision or delay. Split hard budget exhaustion from a negative recommendation so a hook cannot revive exhausted schedule or timeout allowance. Scope this adjustment to session retries, preserving buffered and one-shot retry behavior.

**Alternatives considered** Marking Authentication retryable or forcing an accepted retry would spend same-model policy on failover, misreport retry events and risk an extra primary request. Dispatching the fallback from the step would duplicate runner, context and attribution authority. Reviving the V1 recovery subsystem would duplicate the V2 lifecycle.

## R5 — Revalidate at dispatch and reuse history

**Decision** Read staged intent first, then the existing protected committed value and legacy default. Carry a revision token covering staged revision and presence, and the committed revision when the committed tier supplied the choice. Recheck after asynchronous model resolution, history loading, any preflight compaction and request preparation, at the step’s provider-consumption boundary, since the step itself runs setup before it starts consuming the request. Recheck effective eligibility and variant using the current model resolver after asynchronous preparation. If the token or effective selection changed, re-resolve and rebuild without publishing or crediting the unstarted attempt. Keep a provisional selection across unchanged preflight compaction and use the existing effective model/variant for compaction. A provisional B may already have physically started an automatic compaction summary when C is accepted. Let the summary finish with B’s original model and variant and preserve its compaction attribution. Re-resolve after that work and send the fallback generation on C. Credit fallback-generation identity and attempt telemetry only when the step consumes the generation stream. A prepared B generation superseded before provider consumption yields no physical dispatch, attempt credit or attempt telemetry. Rebuild C’s options and model-specific history before dispatch. Already dispatched work keeps its attribution. Identity remains provider plus model, with variant excluded from the key. Carry the attempted set through the active drain's tool continuations and transient Location move/reload continuation. Reset it at a new turn boundary. Preserve current primary snapshot for ordinary same-model retries.

**Rationale** The existing chooser checks staged changes across a committed read, but `pendingFallback` can be retained across compaction and `attemptedFallbacks` is populated during selection. Those boundaries can stale the choice or count a request that never went out. `SessionHistory` and `to-llm-message.ts` already rebuild model-specific history from settled calls/results and strip incompatible native metadata. `SessionStep` can observe actual local and hosted tool state before cleanup synthesizes failures. Successful normalized results, including an explicitly reported tool error, are durable facts. Interrupted or defecting executing tools and hosted calls with missing results retain unknown effects even when cleanup records a failure.

**Alternatives considered** A request-start fallback or an unconditional pinned candidate across async preparation misses later accepted changes. Patching the model on a prepared request would misattribute options, history or variant. A second store for executed tools would compete with the canonical history. Replaying current-step visible work with no supported continuation boundary is excluded from the distinct fallback path.

## R6 — Observe one SSE transport lifetime

**Decision** Use `Framing.Definition.id === "sse"` at the successful HTTP execution boundary. Register the single completion observer in the existing execution scope after successful response acquisition and selection of SSE framing. A successful HTTP response whose body then fails on its first pull is an established transport error under the Effect response interface. Measure byte pulls in `http.ts` and implement HTTP SSE’s `TransportExecution.complete`. The route already calls the optional acknowledgement after a successful protocol stream end; HTTP currently leaves it absent. Wire the acknowledgement to the same execution scope as classification. Record normal byte exhaustion separately from early scope close and preserve decoder/transport failures. Carry the explicit Promise request signal through a private Effect context reference at the existing `run` and `iterate` boundaries. Use the outer stream exit and observed terminal facts to distinguish owning request interruption, typed failures and downstream scope close. At final classification sample explicit abort state synchronously, set the one-shot outcome before reporting, and detach one Effect-native diagnostic invocation from cleanup using the installed Effect 4.1.0 `Effect.forkDetach({ startImmediately: false })`. Suspend the sink invocation behind an Effect boundary and absorb failures and defects. The default sink uses the existing debug logger with the V1 message. An adapter for a Promise-returning host or test sink lives in `packages/ai/src/index.ts` and exposes an enqueue-and-return Effect via `Effect.sync`. The adapter guards synchronous throws, registers native Promise rejection handling immediately and returns without awaiting delivery. It captures only the immutable summary for delivery and retains no stream scope or waiting fiber if the Promise remains pending. Use an internal scoped diagnostic seam for deterministic tests and integrate no new public option or event.

**Rationale** V1 instruments a Web reader and uses a synchronous guard around its summary callback. V2 owns the bytes, framing and deadline without rebuilding Fetch. The pinned Effect async iterator's `return()` interrupts its current pull, then closes its scope with a successful exit. A pull interruption alone therefore cannot identify abort. Effect's body pulls and timeout machinery already provide observability and cancellation. A protocol may end successfully via `takeUntil` before HTTP EOF, making the existing route acknowledgement useful. `telemetry/splash.ts` observes provider-native protocol timing and should continue to do so independently of client-observed transport timings.

**Alternatives considered** Wrapping Fetch or adding a second body reader would change backpressure, cancellation and native middleware behavior. Inferring abort from error names or an interrupted pull would conflate downstream cancellation with request abort. Logging in read failure plus finalizer would double count. Awaiting a sink would tie transport teardown to diagnostic delivery. Adding the record to normalized session telemetry would falsely attribute transport-observed timing to provider metrics.
